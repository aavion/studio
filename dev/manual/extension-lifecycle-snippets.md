# Extension lifecycle snippets

> **Status**: Draft  
> **Updated**: 2026-06-21  
> **Owner**: Core  
> **Purpose:** Collect extension discovery, validation, dry-run, review, execution, and action-log notes before the installer lifecycle is implemented.  

## Overview

This page captures the current extension lifecycle shape without pretending the installer is finished. Keep it as a source of working notes for installable extensions, cached imports, and future update extensions.

Extensions are the only installable extension unit. Themes, modules, captcha providers, editor providers, and future extension types are extension scopes, not separate top-level extension systems. An extension is active or inactive as one unit; if an extension has both `frontend-theme` and `module` scopes, switching away from that theme deactivates the whole extension instead of trying to split its theme and module parts.

## Current lifecycle sketch

```text
discover candidates
  -> parse manifest
  -> validate EXTENSION_* manifest keys
  -> validate extension shape
  -> run optional lint checks
  -> inspect features
  -> build dry-run/action queue
  -> present review and diffs
  -> execute queue
  -> persist action log
```

## Discovery

Current default extension roots:

| Source | Path | Manifest namespace |
|--------|------|--------------------|
| App | `./.manifest` | `APP_*` |
| Extension | `extensions/*/.manifest` | `EXTENSION_*` |
| Import cache | `var/cache/$APP_ENV/imports/*/.manifest` | open/generic |

Discovery should remain cheap. It should not load extension PHP classes, routes, database contributions, services, or assets. Later lifecycle code can choose when a discovered extension becomes active.

A full discovery run is an explicit lifecycle operation, not request-time work. It should be triggered by an administrator refresh action, installer completion, setup task, scheduler task, or future update-check workflow. The product-level operation covers manifest scanning, `ExtensionValidator` validation, and registry reconciliation, even if the underlying services stay split for testability.

Use `App\Core\Extension\ExtensionDiscoveryRunner` for deterministic registry refreshes. The Admin UI starts that work through the live Operations/ActionLog layer when JavaScript is available and falls back to an immediate POST run for non-JavaScript submissions. Use `App\Core\Extension\ExtensionDiscoveryDispatcher` for installer completion, scheduler tasks, update checks, and other deferred tooling. It queues `ExtensionDiscoveryMessage` through Symfony Messenger and returns a localized `WorkflowResult` immediately. The message handler calls the same runner, which records the trigger context, calls `ExtensionDiscovery`, stops before registry mutation when discovery itself is invalid, catches unexpected exceptions as operation issues, and delegates successful extension candidates to `ExtensionRegistryHandler`.

Manual CLI runs use `php bin/console extensions:discover`; add `--json` for machine-readable output and `--trigger=<name>` when a caller needs to identify the source. The command queues discovery by default. Use `--run-now` only for deliberate recovery or local maintenance where synchronous execution is acceptable.

Deferred Messenger work is drained opportunistically after HTTP responses through `App\Core\Messenger\DeferredMessengerDrainSubscriber`. It checks for due `async` transport rows after the main request has terminated, starts one detached `messenger:consume async` worker when work is pending, and uses a short environment-scoped cache lock to avoid parallel request-triggered workers. Missing database connections or missing `messenger_messages` tables are treated as a no-op so first-run setup and recovery routes stay graceful.

Extension discovery is intentionally not registered as a Symfony cache warmer. Cold container builds must not touch Messenger or database-backed extension state before setup has established the application schema. Setup runs extension discovery after migrations and initial data seeding, then runs `assets:rebuild --trigger=setup --json` so extension-aware translation aggregation happens after discovery and non-blocking rebuild warnings can be surfaced in the setup action log. A future scheduler job should call `extensions:discover` periodically; installer completion and Admin UI refresh actions already provide additional explicit trigger points.

The repository demo extension lives under `extensions/demo-module`. It is intentionally small and inactive after discovery; use it to exercise extension discovery, registry views, scoped assets, extension runtime contributions, and lifecycle UI flows. Demo extensions may include tiny `extension.php` contribution loaders, but they execute only after explicit activation.

Extension Twig validation checks syntax while accepting runtime filters, functions, and tests as extension placeholders. Availability of Symfony, Studio, theme, or extension-provided Twig extensions is verified by render/runtime coverage instead of discovery-time linting.

Required extension manifest keys:

| Key | Purpose |
|-----|---------|
| `EXTENSION_AUTHOR` | Human-readable author or vendor. |
| `EXTENSION_SLUG` | Stable extension identifier and target folder name under `extensions/`. |
| `EXTENSION_NAME` | Human-readable extension name. |
| `EXTENSION_VERSION` | Extension version. |
| `EXTENSION_SCOPE` | One or more scopes, for example `[frontend-theme, system-template]` or `module`. Every real extension needs an identity scope: `module`, a theme scope, or a provider scope. Capability scopes such as `system-template`, `api`, `database`, `content-schema`, `scheduler-tasks`, and `operations` are additive only. |
| `EXTENSION_DEPENDENCIES` | Dependency list, empty when no dependency is required. |

`EXTENSION_SLUG` must be an owner slug: it starts with a lowercase letter, uses only lowercase letters, digits, and single hyphen-separated segments, stays at 60 characters or less, and matches the extension folder name exactly.

Optional well-known keys include `EXTENSION_SOURCE`, `EXTENSION_CHANNEL`, `EXTENSION_IMAGE`, `EXTENSION_NAMESPACE`, `EXTENSION_DESCRIPTION`, `EXTENSION_LICENSE`, and `EXTENSION_HOMEPAGE`; additional extension-owned descriptor keys are allowed as long as they use the `EXTENSION_` prefix and the required keys are present and valid. Extension manifest values are stored as typed immutable metadata and exposed to extension-owned code through `ExtensionSettings::get('{extension-slug}', 'manifest.{manifest_key_without_extension_prefix}')`, for example `EXTENSION_SOMEKEY=hallo welt` on `icon-captcha` becomes `ExtensionSettings::get('icon-captcha', 'manifest.somekey')`. If the extension writes the same key through `ExtensionSettings::set()`, the persisted DB value wins while the manifest metadata remains unchanged. Integer, bigint, float, boolean, and array-like values are typed where safe; ambiguous values remain strings. `EXTENSION_SOURCE` should point to the repository or release source root without a branch suffix, while `EXTENSION_CHANNEL` names the branch or channel; admin UI links may combine both values into a branch-specific URL where the source host supports it. Dependency entries use a compact JSON-like list of `[extension, version-constraint]` pairs such as `[["system",">=0.2"],["demo-frontend-theme","=0.1"]]`. Supported forms are bare compatibility constraints, `>=` minimum version floors, and `=` precision pins: `"1.2.3"` accepts patch releases before `1.3.0`, `"1.2"` accepts minor and patch releases before `2.0.0`, `"1"` accepts `1.0.0` and newer, `>=0.2` means at least `0.2.0`, `=0` accepts versions before `1.0.0`, `=1.0` accepts patch releases before `1.1.0`, and `=1.0.0` pins the patch version. Malformed non-empty dependency declarations are validation errors. The virtual `system` extension is treated as an active dependency backed by the root `.manifest`; real extension dependencies still resolve against the persistent extension registry.

The ZIP installer stages uploads under `var/cache/{APP_ENV}/extension-installs`, verifies the manifest and extension lint rules, then pauses the live operation with a review-required confirmation before copying files. `EXTENSION_SLUG` defines the target folder. If that extension already exists, the apply step removes the existing extension folder first, preserving whether it was active so activation can be restored after discovery. Update execution beyond ZIP uploads is deferred: a later updater should compare registered versions with manifest source metadata and use a narrow Git-backed stub for extension or system updates.

Current identity scopes are `frontend-theme`, `backend-theme`, `module`, `captcha-provider`, and `editor-provider`. Current capability scopes are `system-template`, `api`, `database`, `content-schema`, `scheduler-tasks`, and `operations`. Frontend themes, backend themes, system-template overrides, and provider scopes are single-active scopes: activating a new extension with the same single-active scope deactivates the previously active extension. Module, api, database, content-schema, scheduler-tasks, and operations scopes may be active in parallel unless they are combined with a single-active identity or capability scope. `module` is the neutral identity fallback, not a capability gate. `system-template` allows an identity-bearing extension to override root templates and root CSS tokens. `api` gates extension-owned API endpoints and handlers, `database` gates declarative extension-owned table contributions, `content-schema` gates immutable content schema preset contributions, `scheduler-tasks` gates scheduled callable/action-queue contributions, and `operations` gates extension-owned operation queues.

Deactivation cascades through active reverse dependencies. If an active extension depends on an extension being deactivated, it is deactivated first; this applies to explicit deactivation and to implicit single-active scope conflicts during activation. Activation still resolves dependencies in the opposite direction and activates inactive dependencies with the requested extension.

## Validation

Extension validation is caller-defined. Core should provide the neutral primitives, while extension, import, update, or setup workflows choose required files and directories.

```php
$extensionSpec = ExtensionSpec::create()
    ->requireFile('.manifest')
    ->withLintingChecks();

$result = (new ExtensionValidator())->validate($candidate, $extensionSpec);
```

`extension.php` is optional and must never be included during discovery. It may be included only after validation, either for activation-only contribution reads or active runtime loading. Extensions are trusted code, so only administrators should install them. Extension PHP files are allowed only as root `extension.php` or below `src/`; extension classes should live below an extension-owned root namespace derived from or declared for the extension slug to avoid collisions, and active extension namespaces must not overlap. Language-level `include` and `require` remain blocked in extension PHP. Extension-local Composer payloads are not supported in early releases: root `vendor/`, `composer.json`, and `composer.lock` are blocked because multiple active extensions cannot safely load isolated versions of the same Composer package inside one PHP runtime. Runtime extension PHP may store short-lived extension-owned artifacts through `extension_cache_set($key, $value, $ttlSeconds)`, `extension_cache_get($key, $default)`, and `extension_cache_delete($key)`, durable extension-owned files through `extension_storage_put()`, `extension_storage_get()`, `extension_storage_delete()`, `extension_storage_exists()`, and `extension_storage_list()` below `var/extensions/{APP_ENV}/{extension}/storage`, or ordinary multipart request uploads through `extension_upload_store($uploadedFile, $targetPath, $options)`. Upload imports use the same caller-owned storage boundary, reject traversal and oversized files, and block high-risk executable, server-side, script, SVG, and archive payloads by extension and MIME; ZIP/archive inspection is a later dedicated contract. The backing Symfony services derive the extension slug from the calling file path, scope keys and paths to that slug, enforce TTL and size limits, and prevent cross-extension access. The same caller-attributed runtime boundary exposes `extension_request()` for a redacted current-request snapshot, `extension_content_query()` and `extension_content_get()` for published public content read models visible to the current actor, `extension_can()` for current-actor role, ACL group, and content view/edit/manage decisions, `extension_csrf_token()` and `extension_csrf_valid()` for Symfony CSRF tokens scoped to `extension:{slug}:{intent}`, `extension_cookie_get()`, `extension_cookie_set()`, and `extension_cookie_delete()` for cookies registered by the calling extension through `CookieConsentDefinition`, `extension_trans()` for caller-owned `ext.<extension-slug>.*` translation keys, `extension_settings_get()`, `extension_file_get()`, `extension_asset()`, `extension_asset_url()`, `extension_live_url()`, `extension_api_url()`, `extension_http_request()`, `extension_log()`, `extension_alert()`, `extension_mail()`, `extension_lookup()`, `extension_entity()`, and extension-owned database CRUD helpers. These helpers return safe defaults on invalid or non-extension callers instead of accepting caller-controlled slugs. `extension_request()` does not expose uploaded file contents, temporary paths, raw cookie values, or sensitive header/body/query values. Cookie helpers preserve the registered cookie identity, write through a response queue, and require consent for optional cookies. Content helpers return routing and schema metadata only, not content field payloads, raw revisions, or entity objects. `extension_can()` returns only a boolean and derives the actor from the current security context, not from caller-provided user data. `extension_csrf_valid($intent)` without an explicit token checks `_csrf_token`, `csrf_token`, or `_token` from the current Symfony request. `extension_log()` and `extension_alert()` pass through caller-owned `ext.<extension-slug>.*` translation keys; literals, core keys, and foreign extension keys use the system-owned fallback message to avoid translation-key spoofing. `extension_mail()` is currently a development-stub facade that validates owner-prefixed workflow IDs, recipients, and parameters before writing a structured message-log record; configurable mail workflow contributions, localized default templates, active-extension filtering, purge cleanup, and real delivery are still a follow-up for the mailer contract.

Extension validation ignores development-only metadata such as VCS files, editor settings, `docs/`, `tests/`, and common repository config directories. Public assets belong under `assets/` so the extension asset sync can mirror them. Assets that must stay private to extension code belong under `private-assets/`. Asset file types are not whitelist-limited, but executable/server-side files and bare HTML are blocked inside asset roots because mirrored assets can become publicly reachable. Templates belong under `templates/`. Translation sources belong under `languages/<locale>/*.yaml`, and `languages/en/` is required whenever an extension ships translations. Extension-local PHP Composer dependencies are intentionally not part of the current package contract: root `vendor/`, `composer.json`, and `composer.lock` are blocked rather than validated. Extension-local `assets/node_modules/` is allowed only when `assets/package.json` and a recognized Node lock file are present; node dependency contents are checked only shallowly. `assets/vendor/` and `assets/vendors/` are normal asset paths, not package-manager dependency payloads, so executable/server-side asset restrictions still apply there.

## Feature inspection

Extension inspection currently reports:

- templates;
- public assets under `assets/`;
- any PHP files;
- `src/` PHP files;
- Twig files;
- JSON, YAML, CSS, and JavaScript files.

Use this for debug UI, import review, extension detail screens, and installer preflight summaries. Do not use feature inspection as permission to auto-load code.

## Planning and execution

`ExtensionOperationPlanner` currently maps selected files into deterministic copy actions. It does not decide extension type, dependencies, activation, rollback, database contributions, or permissions.

```php
$planner = new ExtensionOperationPlanner();
$queueResult = $planner->copyFiles($candidate, $projectDir, [
    'templates/base.html.twig',
    'assets/app.css',
], targetPrefix: 'extensions/demo');
```

Extension assets must be self-contained. Extensions should vendor any external JavaScript or CSS dependencies they need instead of making the project inject third-party dependency declarations into the global importmap.

Active extension assets are exposed through generated registries rather than direct runtime discovery. The lifecycle mirrors active extension assets into `assets/extensions/<extension-slug>/` and rewrites stable CSS/JS registry files under `assets/styles/extensions/` and `assets/js/extensions/`. CSS registries may include Tailwind `@source` directives for active extension templates and `@import` directives for mirrored active extension CSS. JavaScript registries use static ESM imports for mirrored active extension JavaScript. Extension-aware asset rebuilds run `ux:translator:warm-cache` after translation aggregation so JavaScript translation assets are present for AssetMapper. They also run `ux:icons:lock`; before that command scans templates, active extension template paths are registered on Twig so extension-owned icon references can be imported locally when Iconify is reachable.

Static extension assets such as images, fonts, SVGs, videos, and vendored dependency files are mirrored but not registered as standalone CSS/JS entries. They are served by AssetMapper only when referenced through mirrored extension CSS, JavaScript, or templates. Source paths under `extensions/<slug>/...` must not leak into public output.

Active extension translations are aggregated during the same rebuild queue. An extension may ship source catalogues as `languages/<locale>/*.yaml`; if it ships any translation source, it must include at least one English catalogue under `languages/en/`. Extension-owned keys must stay below `ext.<extension-slug>.*`. Inactive extension language files are not aggregated, so disabled extension copy cannot affect runtime translation fallback.

Template overrides are scope-bound. Any valid extension scope may ship additive frontend and backend views under `templates/frontend/**` or `templates/backend/**`; only `frontend-theme` and `backend-theme` paths are searched before native templates and can override matching area templates. Module and provider extension paths are searched after native templates, so they can provide extension-specific views without replacing core UI. `system-template` may override root-level shared templates such as `templates/base.html.twig` and `templates/macros/core/**`. Extensions may reference root templates through `@root/...` for fallback behavior even without `system-template`, but they must not replace root templates unless the scope is present. Extension-owned macros are additive and belong under `templates/macros/{extension-slug}/**`.

Provider extension templates use the shared `@provider` namespace. An extension with `EXTENSION_SCOPE=captcha-provider` may ship `templates/provider/captcha/**`; an extension with `EXTENSION_SCOPE=editor-provider` may ship `templates/provider/editor/**`. Active provider extension paths are searched before native `templates/provider/**`, so native provider templates remain the base implementation whenever no matching provider extension is active.

`App\Core\Extension\ActiveExtensionProvider` is the central gate for extension loaders. Twig namespace registration and extension asset sync already use this boundary, and future service, route, database, provider, and scheduler loaders should use it instead of querying `extension` directly so only active real filesystem extensions under `extensions/` can contribute runtime behavior. Virtual records such as the native `system` fallback are intentionally excluded from this gate.

`ExtensionPhpLoader` loads optional active extension `extension.php` files at runtime. Discovery and registry sync never include extension PHP. Activation-only contribution reads use `ExtensionContributionReader`, which registers the addressed extension's declared namespace before requiring `extension.php` so database/content activation factories may live in `src/` classes without running runtime boots. The extension loader may bootstrap an extension-owned namespace, return a callable, return contribution DTOs/providers, or return a `ExtensionContributions` builder for a readable grouped contribution list. Supported direct contributions currently include `StaticViewInjection`, `ConfigurableStaticViewInjectionSet`, `DynamicViewInjection`, `ExtensionSettingDefinition`, scheduler task definitions, API endpoints and handlers, declarative database tables, content schema presets, and `ExtensionOperationDefinition` entries with matching `ExtensionActionQueueProviderInterface` providers; provider objects implementing the matching provider interfaces are also accepted and evaluated during extension loading so provider failures keep extension attribution. API endpoint and handler contributions require `api` scope, database table contributions require `database` scope, and content schema presets require `content-schema` scope. Extension scheduler task definitions may target only owner-prefixed callables or ActionQueues; raw `Command` scheduler tasks are system-owned until a dedicated extension command policy exists. Extension API and live endpoint definitions must declare the owning extension slug as their owner, stay below the extension-owned path namespace, and use extension-owned handler keys. Static injections own menu-aware system views and route targets by surface, configurable static route sets read their stable parent path from extension settings with a declared default, and dynamic injections own content-route slots or variant routes through declarative filters such as real-content-only or schema matching. Runtime view contribution templates are surface-bound: public contributions must render extension-owned `@frontend/{extension-slug}/...` templates, while admin and editor contributions must render extension-owned `@backend/{extension-slug}/...` templates. Registry sync and fault reset validate the full extension tree so later recursive asset mirroring cannot publish files hidden beyond a shallow discovery depth. Hard failures are converted into structured lifecycle diagnostics, mark the extension `faulty`, deactivate active reverse dependents with explicit messages, and run the extension-aware asset rebuild synchronously when the lifecycle is already executing inside an operation or command process. This runtime faulting is intentional health enforcement, not an Admin-only mutation: any main request that first observes broken active extension code may move that extension out of runtime and clean up its dependents so faulty code is not kept active. Admin list, detail, and API read models may invoke the same central loader for an accurate runtime view, but they must not add separate read-path mutations beyond this shared self-protection boundary. Returned iterables are staged before registry mutation, so unsupported later items do not leave partial runtime contributions active for the current request. Extension-local Composer packages are not supported in early releases; extensions should keep PHP runtime code under their own namespace and use documented facades for core-owned services.

Extensions must not ship free-form Doctrine migration classes. Database changes are a core-controlled contribution contract: an extension with `database` scope may declare `ExtensionDatabaseTable` definitions, and activation creates missing tables whose physical names are generated as `{database-prefix}ext{normalized-slug-length}_{normalized-slug}_{local-table}`. The length-prefixed owner segment keeps `demo` and `demo-module` unambiguous after hyphen-to-underscore normalization. The synchronizer refuses names outside that exact owner prefix and does not modify core or other extension tables. Contributed columns use portable DBAL types plus a whitelisted option set of `length`, `notnull`, and scalar `default`; raw DDL options such as `columnDefinition` are not part of the contract. Contributed tables may define primary keys, regular indexes, unique indexes, and foreign keys to other tables owned by the same extension when the referenced columns resolve to a primary key or unique index. Runtime PHP can use `extension_db_fetch()`, `extension_db_insert()`, `extension_db_update()`, and `extension_db_delete()` for bounded CRUD access to its own physical extension tables. The helpers derive the owner slug from the calling extension file, validate local table and column identifiers, parameterize values, cap fetches, require criteria for updates/deletes, and return empty/false/zero results on invalid calls. If table creation fails after one or more SQL statements have already run, the synchronizer attempts to drop the current table together with earlier created tables before reporting failure. Foreign keys to core-owned user, ACL, content, or schema tables are intentionally not part of the current contract because they could couple core deletion semantics to extension data; use `extension_lookup()` and `extension_entity()` for redacted core references instead. Activation is intentionally non-destructive; existing contributed tables are left in place. Reactivation/synchronization may apply only additive updates to existing extension-owned tables after all missing table creation for the same contribution set has succeeded: nullable columns, columns with scalar defaults, and new indexes. Column drops, column type or option changes, index drops or renames, primary-key changes, required columns without defaults, and foreign-key changes are rejected with explicit diagnostics. Larger schema rewrites should create a new extension-owned table, migrate data through extension-owned runtime code, and switch to the new table; dropping the old table after migration requires a later explicit cleanup contract. Purge drops only tables matching the same physical extension owner prefix.

Extensions with `content-schema` scope may contribute `ExtensionContentSchemaDefinition` presets. Core stores them as locked `ContentSchemaSource::Module` schemas using identifiers derived from `ext{normalized-slug-length}_{normalized-slug}_{schema-name}` so overlapping extension/schema names stay collision-free. If a contributed definition changes, activation creates a new schema version and activates it; unchanged definitions are left alone. An existing non-module schema with the generated identifier is a collision and is not reused for extension versions. Purge force-archives content items that still point at extension-owned presets, deletes unreferenced presets, and retains referenced presets as disabled database copies when content items or historical revisions still hold foreign keys. The operation result must warn about retained schemas and list the retained identifiers so operators can decide whether to migrate or copy that content later. User-editable copies should be created as normal custom schemas when an operator wants to diverge from the immutable preset, and those custom copies are not removed by extension purge.

Deactivating an extension with contributed content schemas must include a content impact pass. The lifecycle review should list content items that directly use extension-owned schema presets, sorted by resolved slug hierarchy, so an operator can explicitly confirm that published or scheduled items will be removed from public rendering. The deactivation operation should archive/unpublish those directly affected items before the extension becomes unavailable, including when deactivation cascades from another extension action. Faulty-extension and automatic cascade paths cannot ask for confirmation, but they must still prefer making affected content non-public over leaving renderable content tied to unavailable schema code. Reactivation must not automatically republish previously archived content: between deactivation and reactivation, an operator may have edited, archived, deleted, or copied content to a custom schema. Reactivation may surface a restore candidate list, but automatic status restoration is explicitly out of scope unless a future editorial workflow records and confirms a durable per-item restore journal.

Simple extension settings are registered through `ExtensionSettingProviderInterface`. An extension setting definition provides extension name, key, label, default value, value type, optional input type, description, option list, validation metadata, arbitrary metadata, and sort order. The core `ExtensionSettingRegistry` exposes definitions only for active extensions, and `ExtensionSettings` stores values in `extension_setting_entry` instead of global configuration. Keys below `manifest.*` are reserved as typed fallback reads from immutable manifest metadata, but can still be persisted through `ExtensionSettings::set()` when an extension intentionally wants a DB override. Admin Settings owns the generic extension settings overview at `/admin/settings/extensions` and extension-specific pages below `/admin/settings/extensions/{extension-slug}`; extensions that need complex workflows should register their own views outside the settings tree.

`faulty` is a registry exit state, not a hidden archived state. During a later automatic discovery run, an unchanged faulty extension stays `faulty` and is not revalidated just because discovery ran again. This avoids rebuild/cache-warmup/discovery loops without a clear operator action. Revalidation happens when discovery sees a meaningful extension change such as a new manifest version or changed extension path, or when an administrator explicitly resets or repairs the lifecycle state. Even after a successful revalidation, the extension returns to `inactive`, not `active`, so dependency checks, conflict handling, and rebuild logging remain auditable.

`ExtensionFaultResetter` is the non-destructive repair path for faulty extensions. It rediscovers only the registered extension directory, validates the current manifest and extension files, preserves compact fault metadata under `last_fault`, and resets the extension from `faulty` to `inactive` only after validation succeeds. It does not delete extension data, remove the extension folder, purge registry rows, or activate the extension. Use purge only for explicit data cleanup after removal.

Asset ordering should be deterministic: native system assets first, active module/provider extension assets next, active frontend theme extension assets next, and active backend theme extension assets last so scoped theme overrides win where CSS/JS order matters. Project-local or entity-local assets remain closer to the rendered element and may be more specific by design.

Use `php bin/console assets:rebuild` as the global rebuild operation after extension activation, deactivation, update, uninstall, setup, or manual admin recovery. Add `--queue --trigger=<name>` only when the caller intentionally wants an explicit deferred rebuild outside an already-running lifecycle operation. Setup runs the command synchronously in its own subprocess so memory and execution time are isolated from the setup runner process. Lifecycle services trigger one synchronous extension-aware rebuild after all extension state changes in the operation have been flushed, not once per extension. Runtime extension exits such as hook failures, missing active extensions during discovery, or PHP loader failures run the same rebuild synchronously inside the current operation boundary so stale active assets/templates/translations are cleaned up before the operation reports success. It should run as an ActionLog-backed operation with persisted step entries and progress metadata. The extension mirror and registry rewrite step runs before Tailwind; translation aggregation writes `translations/runtime/{APP_ENV}/messages.{locale}.yaml`, and `ux:translator:warm-cache` writes `var/translations` before AssetMapper work. `cache:clear` runs last so the live operation UI is not invalidated before the rebuild has already produced mirrored assets, registries, Tailwind output, active translation catalogues, JavaScript translation assets, and production asset-map output.

Live extension actions should enter the Operations/ActionLog layer through contribution-based operation definitions and action-queue providers, not free shell/process helpers. An active extension can expose an owner-prefixed `ExtensionOperationDefinition` such as `demo-module.cleanup` with caller-owned `ext.<extension-slug>.*` label and description keys, then provide the matching `ExtensionActionQueueProviderInterface`. The shared `extension.operation` live-operation provider loads active extensions, validates the requested extension/target pair, sanitizes scalar/array payload values, and starts only registered extension-owned targets. Scheduler tasks may target the same registered action queues through `SchedulerTaskType::ActionQueue`; extension action queues remain untrusted and follow the existing scheduler confirmation policy. If review is needed during a live flow, the provider should emit a user-facing action-required prompt and a safe continuation descriptor; the follow-up apply step is a new live operation, not a suspended process.

`ExtensionRuntimeFailureSubscriber` listens to public hook failure diagnostics and delegates to `ExtensionRuntimeFailureHandler`. If the failing extension can be identified and is active, the handler records runtime-failure metadata, marks the extension `faulty`, deactivates active reverse dependents with a `extension.lifecycle.dependent_deactivated` message, and runs the extension-aware asset rebuild synchronously. If ownership is unknown, the hook failure remains a structured issue without changing extension state.

`ExtensionRemover` prepares the removal boundary for later Admin UI and installer flows. Removal deactivates an active extension first, deletes the extension directory, marks the registry row as `removed`, and can trigger the same extension-aware asset rebuild. Purge is separate and only available for already removed extensions: it calls `ExtensionLifecycleCleanupRunnerInterface` for extension-owned cleanup and then deletes the registry row. The default cleanup runner removes extension-scoped settings, drops extension-owned database contribution tables, deletes unreferenced extension-owned content schema presets, and retains still-referenced presets as disabled schema copies with warning messages. If the extension directory still exists after purge, later discovery can register it again.

## Open notes

- Dependency maps are intentionally deferred to installer/lifecycle routines.
- Discovery does not run during normal requests.
- Automatic discovery is limited to fresh container boot or cache rebuild flows.
- Manual discovery triggers include Admin UI refresh, installer completion, scheduler task, and future update-check workflows.
- Extension signatures and checksums belong to update/release workflows.
- Activation must be separate from discovery.
- Failed activation should roll back to the previous active extension state where practical.
- Extension-owned data deletion needs explicit confirmation and action-log coverage before the cleanup runner performs destructive work.
- Extension-owned database tables are named by core as `{database-prefix}ext{normalized-slug-length}_{normalized-slug}_{local-table}`.
- Deactivation must not drop data. Uninstall may offer data removal through an extension purge routine.
- Theme, system-template, and provider scopes are single-active; module, api, database, content-schema, scheduler-tasks, and operations scopes are many-active unless combined with a single-active scope.
