# User Account Lifecycle Hardening Slice

> **Status**: Draft  
> **Updated**: 2026-05-28  
> **Owner**: Core  
> **Purpose:** Track account-status side effects for the user-management feature slice.

## Checklist

- [x] Add one service boundary for account status changes so controllers do not duplicate lock/delete side effects.
- [x] Revoke active API keys when an account becomes inactive or deleted.
- [x] Revoke pending password-reset and security-review tokens when an account becomes inactive or deleted.
- [x] Keep active status changes non-restorative; previously revoked keys and tokens stay revoked.
- [x] Apply lifecycle side effects to admin status edits, review-queue deletes, and password-change dispute locks.
- [x] Let users close their own account with password confirmation and explicit confirmation.
- [x] Include side-effect counts in audit contexts.
- [x] Emit a deterministic `account.closed` mail flow when users close their own account.
- [x] Cover admin status locks, user-triggered dispute locks, and user-triggered account closure with controller tests.

## Notes

Inactive and deleted users already cannot pass form-login checks. This slice makes that lock meaningful for adjacent credentials as well: API keys stop being active and pending recovery/security-review tokens stop being usable once the account is no longer usable.

Self-service account closure uses the same lifecycle path as administrative locks and deletes. The profile form requires the current password plus an explicit confirmation checkbox, then marks the account deleted, emits the `account.closed` mail flow through the delivery stub, invalidates the session, and redirects back to login with a neutral closure notice.
