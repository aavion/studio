# Backup and restore (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for basic backup, restore, and database cloning workflows for development and staging environments.  

## Overview
- Defines basic backup and restore capabilities for the CMS.
- Covers database cloning, storage targets, environment safety, restore validation, and development/staging workflows.
- Depends on setup automation, import/export, and security decisions.
- Separates operational recovery from collaboration import/export.

## Outline
Backup/restore should protect project data and support development/staging cloning. It should not be confused with content import/export. Backups are operational snapshots; imports are reviewed structured changes.

The first backup workflow should be conservative: explicit commands, dry-run or validation where useful, confirmation before restore, clear target environment checks, and useful logs. Restores should protect against accidental production data overwrite and should verify compatibility before applying data.

Database cloning for development and staging should be supported in a controlled way. It should handle database data, uploaded files, generated assets where needed, manifests, and package compatibility metadata.

## Technical Specifications
- Provide Symfony Console commands for backup, restore, and clone workflows.
- Use Flysystem where storage abstraction is useful.
- Use local filesystem storage through Flysystem as the first supported backup target.
- Keep storage adapters replaceable through explicit contracts.
- Include database content and required file storage in backup scope.
- Prioritize full backups first, while keeping the design open for incremental or differential backups later.
- Include manifest and compatibility metadata.
- Validate application version, module versions, theme versions, and database compatibility before restore.
- Require confirmation for destructive restore operations.
- Provide dry-run or inspect mode before restore.
- Provide a basic restore dry-run diff, for example counts of new, removed, and changed entities where practical.
- Log backup and restore operations with actor, source, target, size/summary, and result.
- Use Messenger for long-running backup/restore jobs only after job state tracking exists.
- Ensure package-owned tables are included when packages are enabled.
- Keep secrets out of portable backup metadata unless explicitly handled by a secure environment-specific process.

## Testing & Validation
- Test command input validation.
- Test backup manifest creation.
- Test restore compatibility checks.
- Test dry-run output for restore.
- Test restore dry-run reports basic counts for new, removed, and changed entities where practical.
- Test fixture backup and restore in an isolated test environment.
- Test package-owned tables are included when package fixtures exist.
- Test failed restore behavior and logs.

## Implementation Notes
- **Decision recorded:** Implement backup/restore as Symfony Console workflows first.
- **Decision recorded:** Use Flysystem-compatible storage boundaries where useful.
- **Decision recorded:** First supported backup storage target is local filesystem storage through Flysystem.
- **Decision recorded:** Prioritize full backups first while keeping the design open for incremental or differential backups later.
- **Decision recorded:** Keep destructive restore behind explicit confirmation.
- **Decision recorded:** Restore should run validation and a basic dry-run diff before apply where practical.
- **Decision recorded:** Restore rollback starts conservatively: require or recommend a backup/snapshot before restore, stop on failure, and provide recovery logs/instructions instead of complex automatic rollback in early releases.
