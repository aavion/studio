# ACL Management Hardening Slice

> **Status**: Draft  
> **Updated**: 2026-05-28  
> **Owner**: Core  
> **Purpose:** Track the administrative ACL guardrails needed to keep user management safe before richer content administration arrives.

## Checklist

- [x] Block administrators from editing users with a higher effective access level.
- [x] Block self-lockout through status changes, group assignment, group level changes, or group deletion.
- [x] Keep at least one active user with Admin-area access after user or group changes.
- [x] Prevent administrators from assigning, creating, or raising groups above their own effective access level.
- [x] Add ACL group impact analysis for user memberships, pending account tokens, content items, schema versions, and site menu items.
- [x] Require explicit review confirmation before ACL group updates and deletes.
- [x] Remove deleted group identifiers from all known ACL-bearing entities.
- [x] Expand audit context for user and ACL group changes with before/after values and impact summaries.
- [x] Cover user-edit policy, group review, and group cleanup behavior with controller tests.

## Notes

ACL group identifiers are intentionally stored in JSON ACL fields on content and navigation records instead of foreign keys. Deleting a group therefore needs an application-level cleanup pass so future content and navigation ACL resolvers do not carry orphaned group identifiers.

The first review flow stays inside the Admin Users controller instead of starting a Live Operation. That keeps the slice small while still making high-impact ACL group edits deterministic: the first submit renders the impact dry run, and the confirmation submit applies the change or cleanup.
