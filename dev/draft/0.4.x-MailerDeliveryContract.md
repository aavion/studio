# Mailer Delivery Contract

> **Status**: Draft
> **Updated**: 2026-06-05
> **Owner**: Core
> **Purpose:** Track the future mailer registry and delivery contract. Account flows are the first built-in registry entries.

## Direction

The mailer UI must learn available templates and replacement parameters from the mail context, not from whichever feature happens to send a mail. `App\Mail\MailFlowRegistry` is the current single source for mail flow metadata. It stores deterministic flow/template keys, grouping and label translation keys, and the allowed parameter keys for each template.

Later, core features and packages should register mail flows through a provider interface, including default Markdown templates and parameter metadata. Until that extension point exists, the registry is hard-coded with the account-management flows listed below.

The future Mailer settings page should be deliberately small: a grouped template dropdown, a language dropdown, and one editor for the selected localized template. The editor should show a compact legend of the available replacement keys for the selected flow, for example `email`, `username`, `action_url`, `expires_at`, and `user_uid`. Template labels and groups should be localized through deterministic translation keys, while the flow/template identifiers remain stable machine keys.

Templates should be stored as localized Markdown. The mailer renders Markdown into standards-compliant HTML mail, creates a plain-text fallback where practical, replaces known `[key]` placeholders from the delivery context, and queues the final message through Symfony Messenger. The first send worker should include a conservative transport guard, for example a small per-run limit and a cooldown between runs, so SMTP rate limits are not hit accidentally. Exact values remain open until real transport behavior is tested.

Locale selection follows the account-flow contract already implemented: public flows prefer the target user's stored language, then the current request locale; administrator-triggered flows prefer the target user's stored language, then the configured default language. If a template is missing for the chosen language, the mailer should fall back to the default language and record a safe message-log warning.

## Built-In Account Flows

| Flow/template key | Purpose | Parameters |
|-------------------|---------|------------|
| `account.invitation.link` | User invitation setup link. | `email`, `action_url`, `expires_at` |
| `account.registration.link` | Auto-approved or admin-approved registration setup link. | `email`, `action_url`, `expires_at` |
| `account.password_reset.link` | Password-reset setup link. | `email`, `username`, `action_url`, `expires_at` |
| `account.registration.approval_requested` | Admin notification for a registration that requires approval. | `email` |
| `account.registration.approved` | User notification that a registration was approved. | `email` |
| `account.registration.rejected` | User notification that a registration was rejected. | `email` |
| `account.registration.existing_account` | Enumeration-safe notice for a registration attempt with an already registered address. | `email`, `username` |
| `account.password.changed` | User notice after a password change, including the security-review action link. | `email`, `username`, `action_url`, `expires_at` |
| `account.password_change.disputed` | Admin notification after a user clicks the password-change dispute link. | `email`, `username`, `user_uid` |
| `account.password_change.reactivated` | User notice after an admin reactivates a disputed account with a random password. | `email`, `username`, `user_uid` |
| `account.closed` | User confirmation after closing their own account. | `email`, `username`, `user_uid`, `retention_days` |

Locale resolution currently follows the delivery context: public flows prefer the user's stored language, then the current request locale; admin-triggered flows prefer the target user's stored language, then the configured default language.

## Audit Decisions

- **Decision recorded:** Mail locale resolution should use the central locale preference resolver once it exists, but mail keeps a deliberate recipient-first fallback: recipient preferred language first, then current request locale for public flows or configured default language for administrator-triggered flows.
- **Decision recorded:** The message-log delivery stub may remain available only as an explicit debug aid once real mail delivery exists. In production-like environments it must be gated by `APP_DEBUG` or equivalent debug configuration and accompanied by strong administrative warnings because clear action URLs contain one-time credentials.
- **Decision deferred:** Enforcing debug-only account-link logging is deferred until Symfony Mailer delivery exists. Before that point the message-log stub is the only retrievable delivery path for setup, invitations, registration, password reset, password-change review, account closure, and APP_SECRET rotation recovery flows, so blocking it would break required account operations instead of hardening them.

## Notes

The real mailer will render localized Markdown templates to HTML and enqueue mail sending through Messenger. Until that service exists, `MessageLogAccountLinkDelivery` writes the exact payload shape the mailer boundary should receive into the message log. Link mail flows receive absolute `action_url` values from the shared absolute URI generator, which accepts already absolute URLs or resolves routes against configured `site.url`. URI-generation failures should surface to the calling UI as generic delivery failures and must not log route parameters or tokens. The action URL intentionally contains the current one-time token for local debugging; production delivery must replace or gate this stub before release.

The mailer registry should stay in the mail context. Account flows pre-fill it today, but later feature modules should not invent parallel user-specific template registries.
