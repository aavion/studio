# Scheduler (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-24  
> **Owner**: Core  
> **Purpose:** Draft for configured scheduled maintenance and package tasks through CLI and protected web entry points.  

## Overview
- Provides a scheduler for administrator-defined recurring tasks.
- Exposes a CLI interface through `bin/scheduler`.
- Reserves `/scheduler/**` as a protected web-accessible execution prefix.
- Uses API-key authentication for web execution.
- Reuses operational action logs and result summaries where possible.
- Supports core maintenance, package-provided tasks, backups, cleanup, indexing, cache rebuilds, and similar recurring operations.

## Outline
The scheduler should let administrators define recurring tasks without relying on direct shell access for every operation. A system cron, hosting control panel, uptime monitor, or external scheduler can call `bin/scheduler` or `/scheduler`, and the application decides which configured tasks are due.

The CLI and web entry points should produce comparable output. Each run should list:

- tasks that were due and executed successfully;
- tasks that were due and failed;
- tasks that are configured but not yet due;
- the next due timestamp for tasks that remain active;
- tasks that were disabled because they failed too often.

Tasks are not executed continuously. A task becomes due when its configured interval has elapsed. The next scheduler run marks due tasks as running and executes them. This keeps the scheduler host-agnostic: a site owner can call it every minute, every five minutes, or from a managed web cron endpoint, while task-level intervals still decide what actually runs.

The initial task set should cover common maintenance needs:

- log rotation and retention-aware cleanup;
- stale entity cleanup based on configured retention;
- package-contributed tasks registered through documented contracts;
- backup creation;
- cache cleanup or rebuild workflows;
- search, resolver, or reference-index rebuilds;
- provider-specific updates such as GeoIP databases or captcha housekeeping when implemented.

Failed tasks should remain due so the next scheduler run can retry them. After three consecutive failed executions, the scheduler should automatically deactivate the task and report that it needs administrator attention. Administrators can fix the cause, review the latest failure output, and manually reactivate the task.

## Technical Specifications
- Add `bin/scheduler` as a thin CLI wrapper for a shared scheduler runner service.
- Reserve `/scheduler/**` as a protected route prefix for web-triggered scheduler runs.
- Require a valid API key for `/scheduler/**`.
- Accept API keys through `Authorization: Bearer <key>` as the primary web authentication mechanism.
- Accept a GET parameter fallback for edge-case hosting environments that cannot send custom headers.
- Recommend using a read-only API key for external scheduler pings unless a future task explicitly requires write-scoped scheduler access.
- Do not expose `/scheduler/**` as a public content route or normal frontend route.
- Keep CLI and web behavior backed by the same scheduler runner and result DTOs.
- Return machine-readable JSON from the web endpoint by default.
- Let `bin/scheduler` support a human-readable summary and a JSON mode for automation.
- Store scheduler task definitions in the database so the Admin UI can create, update, activate, deactivate, and inspect tasks.
- Store task fields such as identifier, label translation key, provider/source, enabled state, interval expression, last run timestamp, next due timestamp, consecutive failure count, and safe metadata.
- Use a portable interval model first, for example seconds/minutes/hours/days plus optional future cron-like expressions.
- Mark tasks due based on stored `next_due_at`, not by scanning historical logs.
- Lock task execution so overlapping scheduler calls do not run the same task twice.
- Prefer database row-level locking or a portable lock service abstraction compatible with SQLite, MariaDB/MySQL, and PostgreSQL.
- Keep task execution idempotent where practical.
- Let due tasks execute in a deterministic order, for example priority, next due timestamp, then identifier.
- After a successful run:
  - reset consecutive failure count;
  - write last run metadata;
  - compute and store the next due timestamp.
- After a failed run:
  - increment consecutive failure count;
  - keep or immediately recompute due state so the task remains eligible for retry;
  - disable the task after the third consecutive failure;
  - keep the latest failure summary for the Admin UI.
- Treat skipped or not-due tasks as successful scheduler outcomes, not operation failures.
- Reuse `ActionQueue`, `OperationExecutor`, `ActionLog`, `OperationResult`, and message severity conventions for task execution where applicable.
- Allow package-provided tasks only through documented registration hooks or tagged services once package runtime integration exists.
- Persist enough task run summary data for Admin UI troubleshooting without turning the scheduler table into a full audit log.
- Send high-impact scheduler events to the future audit/logging system, including task creation, activation, deactivation, repeated failure disablement, backup execution, cleanup execution, and package task execution.
- Keep sensitive task configuration redacted in CLI, JSON, action logs, and audit summaries.
- Avoid storing raw API keys in scheduler configuration or logs.
- Return appropriate HTTP status codes for the web endpoint:
  - `200` when the scheduler ran and produced a summary, even if individual tasks failed;
  - `401` when the API key is missing or invalid;
  - `403` when the API key is valid but not allowed to run the scheduler;
  - `429` when future rate limiting rejects excessive calls;
  - `503` when maintenance or lock contention prevents execution and the caller should retry later.

## Admin UI
- Provide an Admin UI list of configured scheduler tasks.
- Show enabled/disabled state, source, interval, last run, next due timestamp, latest result, and consecutive failure count.
- Allow administrators to create core task instances where the task type supports configuration.
- Allow administrators to activate, deactivate, run now, and reset failure state.
- Require explicit confirmation for tasks that are destructive or high-impact.
- Show package-provided tasks only after their package is active and task registration has passed validation.
- Disable or hide package-provided task types when the package is inactive.
- Preserve task definitions where possible when a package is deactivated, but do not execute them until the package is active again.

## Security Notes
- `/scheduler/**` must be treated as a protected operational endpoint, not as an external public API.
- Bearer authentication is the preferred transport for API keys.
- GET-token authentication is allowed only as an edge-case fallback for constrained hosting environments.
- If GET-token authentication is used, documentation should warn that URLs can appear in logs, browser history, reverse proxies, and monitoring tools.
- Read-only API keys are recommended for scheduler calls because the scheduler endpoint itself decides which configured tasks may run.
- If future task classes require elevated write semantics, the scheduler runner should enforce that per task instead of globally assuming all scheduler callers can mutate state.
- Scheduler output must not leak protected config values, API keys, passwords, upstream credentials, backup paths containing secrets, or full exception traces in production.

## Testing & Validation
- Test CLI and web entry points call the same scheduler runner.
- Test Bearer API-key authentication for `/scheduler/**`.
- Test GET parameter API-key fallback with redacted logs.
- Test missing, invalid, revoked, and insufficient API keys.
- Test due task selection by `next_due_at`.
- Test not-due tasks are reported with next due timestamps.
- Test successful task execution updates last run, next due, and failure count.
- Test failed task execution remains due and increments consecutive failure count.
- Test the third consecutive failure disables the task.
- Test manually reactivating a disabled task resets or preserves failure metadata according to the final Admin UI decision.
- Test overlapping scheduler runs cannot execute the same task twice.
- Test package-provided task registration and deactivation behavior once package runtime hooks exist.
- Test retention cleanup tasks do not delete data outside configured scopes.
- Test JSON output remains stable enough for external scheduler monitoring.

## Implementation Notes
- **Decision recorded:** Scheduler execution should be available through both `bin/scheduler` and `/scheduler/**`.
- **Decision recorded:** `/scheduler/**` requires a valid API key, preferring Bearer tokens and allowing GET-token fallback only for constrained environments.
- **Decision recorded:** Scheduler summaries should report successful tasks, failed tasks, and not-yet-due tasks with their next due timestamps.
- **Decision recorded:** Failed tasks remain due and are retried on future scheduler runs.
- **Decision recorded:** A task is automatically disabled after three consecutive failed runs.
- **Decision recorded:** Admin-defined tasks should live in the database and be configurable from the Admin UI.
- **Decision recorded:** Package-contributed tasks are allowed later through documented registration contracts.
- **Decision recorded:** Scheduler runs should reuse the shared operational action-log/result model where possible.
- **Open:** Decide the exact interval expression model for the first implementation.
- **Open:** Decide whether scheduler run summaries need a dedicated table or can start as state markers plus action logs.
- **Open:** Decide whether read-only API keys are always sufficient for scheduler execution or whether specific task classes may require write permission.
