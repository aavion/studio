# IconCaptcha integration (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-06-15   
> **Owner**: Core  
> **Purpose:** Draft for an optional IconCaptcha provider module built on the generic captcha extension contract.  

## Overview
- Defines the planned IconCaptcha implementation as a replaceable provider module.
- Depends on security, setup, error handling, public form workflows, and plugin module extensibility.
- Belongs to the broader security hardening cut, but should be implemented in its own provider branch after the generic captcha contract lands.
- Keeps the CMS core focused on a generic captcha contract while allowing IconCaptcha to ship its own services, templates, assets, translations, and validation rules.
- Uses the old Grav `sec-lookup` implementation only as inspiration. No old code, secrets, or hard-coded asset paths should be copied into the Symfony project.

## Outline
IconCaptcha should be treated as one possible captcha provider, not as a hard-coded core dependency. The security draft defines the generic captcha resolver, workflow configuration, rate limiting, validation feedback, and extension boundaries. This draft describes how a first-party IconCaptcha module can implement that contract without leaking provider-specific behavior into public forms.

The first implementation should avoid coupling public forms directly to IconCaptcha classes. Contact forms, login throttling, registration, anonymous submissions, or future public workflows should ask the captcha resolver for the configured provider and handle validation failures through the shared error handling and validation model.

The core captcha integration should expose a global form field. When a workflow includes that field, the field resolves the configured provider and delegates rendering and validation to it. If the configured provider is `none`, or no captcha provider module is available, the field should validate successfully to avoid breaking public workflows.

The provider module should own its icon and emoji assets. These assets should live inside the module package rather than in the application core so IconCaptcha remains removable and replaceable. The core should only know that the selected provider can render a challenge, validate a submitted answer, and report recoverable validation failures.

The challenge should be deterministic from server-side state, but unpredictable to the client. A challenge ID, timestamp, request context, and application/module secret can derive the icon pool, target icon, and button order. The server can then recompute the expected answer during validation without persisting the whole challenge payload. The challenge ID must still be marked as used after validation to prevent replay.

The frontend should keep the interaction lightweight and accessible: one target icon, a fixed button grid, hidden form fields for challenge metadata, a refresh control, and clear error feedback from the normal form validation layer. A two-slot challenge approach is preferred for smooth refresh behavior: switch immediately to a standby challenge, then refill the hidden slot asynchronously.

IconCaptcha must work together with other abuse-control layers. Honeypots, CSRF, route-specific rate limits, form validation, suspicious-request tracking, and optional GeoIP/security policy all remain separate signals. Captcha success should not bypass ACLs, CSRF, or business validation.

## Technical Specifications
- Implement IconCaptcha as a first-party package with `captcha-provider` scope, for example `packages/icon-captcha/`.
- Store provider assets in the module package, for example `assets/icons/` and `assets/emoji/`.
- Use package-owned templates, styles, JavaScript, translations, and PHP services.
- Keep the package compatible with the module manifest rules from the plugin modules draft.
- Register IconCaptcha through the generic captcha provider contract, for example a tagged provider service.
- Keep provider selection configurable per workflow through core-owned configuration.
- Allow workflows to select `none`, `icon_captcha`, or a future module-provided provider where appropriate.
- Expose IconCaptcha as one selectable provider in the global captcha provider configuration.
- With only the first-party provider installed, the available provider choices should be `icon_captcha` and `none`.
- Treat provider value `none` as automatic captcha success.
- Treat missing or disabled captcha provider modules as automatic captcha success unless a later security policy explicitly marks the workflow as provider-required.
- Use the global captcha form field instead of workflow-specific IconCaptcha fields.
- Use contact forms, registration forms, and guest comments as the first expected captcha-protected workflows.
- Keep the provider removable. Disabling or uninstalling the module must not break workflows that can fall back to another provider or to `none`.
- Do not store provider secrets in the module manifest, docs, committed config, or public assets.
- Generate or configure any provider secret through setup/module configuration and store it in a local secret/config location.
- Bind challenge derivation to server-side secret, challenge ID, timestamp, session identifier where available, user agent, and route or workflow key.
- Keep the public challenge payload limited to data needed for rendering and validation submission.
- Mark challenge IDs as one-shot values in a Symfony cache pool after validation, regardless of success or failure.
- Expire challenges after a short configurable TTL.
- Use cache pools or another Symfony-native storage mechanism for used challenge IDs and short-lived challenge metadata.
- Sanitize SVG assets before rendering inline SVG in buttons, or serve them through a trusted static asset path with a fixed allowlist.
- Keep icon identifiers stable and non-sensitive.
- Use fixed-size UI elements so the challenge does not shift the form layout.
- Use accessible controls: real buttons, `aria-pressed` or equivalent state, keyboard navigation, and non-visual labels through translations where needed.
- Provide a refresh endpoint or provider action that returns a fresh challenge without caching.
- Keep refresh endpoints lightweight. If refreshes are served through `/api/live/**`, aggressive abuse should feed passive security signals instead of normal rate-limit `429` responses.
- Refresh challenges after browser back-forward cache restores.
- Use Symfony Validator constraints, form-level validation, or a shared captcha form field type for user-facing errors.
- Send recoverable captcha errors through the normal validation and error-handling flow.
- Treat honeypot failures as suspicious signals that may be silent, while normal missing/expired/wrong captcha input should be recoverable for humans.
- Use Symfony RateLimiter alongside captcha checks. Prefer separate buckets for form posts, captcha failures, and suspicious probe traffic, while `/api/live/**` challenge refreshes remain passive abuse signals.
- Reset or soften the relevant scoped limiter buckets after successful captcha validation when the workflow policy allows it, so human users are not unnecessarily penalized.
- Avoid a single coarse per-IP bucket as the only rate-limit mechanism.
- Consider progressive response behavior: allow, throttle, require captcha, then block only for strong signals.
- Log provider failures with safe context such as workflow, route, failure code, and anonymized request identifiers where appropriate.
- Do not log submitted choices, generated seeds, full challenge payloads, session IDs, raw IPs beyond the project privacy policy, or secrets.
- Keep templates theme-compatible, but do not require themes to know provider internals.
- Allow the system theme to style the provider through stable wrapper classes or CSS custom properties.
- Keep replacement open for third-party captcha providers.

## Suggested Flow
```text
render_form(workflow):
    provider = captcha_resolver.provider_for(workflow)
    if provider is none:
        render no challenge
        return
    challenge = provider.create_challenge(request, workflow)
    render provider challenge template

submit_form(workflow):
    provider = captcha_resolver.provider_for(workflow)
    if provider is none:
        return success
    result = provider.validate_submission(request, workflow)

    if result.failed_recoverably:
        add translated form validation error
        record safe failure metric
        stop form processing

    if result.failed_suspiciously:
        record suspicious signal
        optionally stop silently or require another challenge

    continue normal form validation and business processing
```

## Failure Model
- `missing`: Required captcha fields were not submitted.
- `expired`: Challenge timestamp exceeded the configured TTL.
- `reused`: Challenge ID was already consumed.
- `invalid_choice`: Submitted choice is outside the expected button range.
- `wrong_choice`: Submitted choice does not match the recomputed answer.
- `context_mismatch`: Request context no longer matches the challenge context.
- `asset_error`: Required icon assets cannot be loaded or rendered.
- `provider_disabled`: Workflow selected IconCaptcha, but the module/provider is unavailable.

Recoverable failures should produce translated form errors. Suspicious failures may also contribute to security scoring, but should not expose challenge internals to the user. If the configured provider is `none`, captcha validation succeeds without producing a challenge or failure.

## Testing & Validation
- Test provider selection through the generic captcha resolver.
- Test global captcha form field integration.
- Test successful and failed captcha validation paths.
- Test recoverable validation feedback on public forms.
- Test rate-limited captcha failure behavior where applicable.
- Test successful captcha validation resets or softens relevant scoped limiter buckets.
- Test that disabling IconCaptcha or selecting another provider does not break workflows using the generic contract.
- Test provider value `none` validates successfully.
- Test missing or disabled provider modules validate successfully unless a later provider-required policy is introduced.
- Test contact form, registration form, and guest-comment workflow configuration once those workflows exist.
- Test challenge generation produces valid payloads without storing secrets in the response.
- Test deterministic recomputation accepts the correct answer and rejects wrong choices.
- Test used challenge IDs cannot be replayed.
- Test expired challenges fail cleanly.
- Test context-bound challenges fail when submitted in an invalid workflow or route context.
- Test refresh endpoint responses are uncached and feed passive abuse signals without normal `/api/live/**` rate-limit rejection.
- Test browser back-forward cache recovery refreshes stale challenges.
- Test SVG/icon asset loading, allowlisting, and sanitization behavior.
- Test keyboard interaction and accessible button state where practical.
- Test translation keys for visible provider labels, buttons, and validation errors.
- Test that provider failure logs do not contain secrets, seeds, raw challenge internals, or disallowed personal data.
