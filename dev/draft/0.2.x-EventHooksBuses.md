# Event hooks and buses (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for modular event handling, hooks, message buses, and replaceable workflow behavior.

## Overview
- Defines the event and hook system used by core features and plugin modules.
- Covers synchronous hooks, asynchronous processing, message buses, and extension safety.
- Supports modular content, import/export, logging, and operational workflows.
- Clarifies which events are public extension contracts and which are internal lifecycle events.

## Outline
Events should make lifecycle boundaries visible and extensible without hiding the core control flow. The system should use Symfony EventDispatcher for synchronous lifecycle notification and controlled extension hooks, and Symfony Messenger for asynchronous work or delayed side effects.

Public extension events are part of the module/theme contract only when documented. Internal events may still exist to keep feature code decoupled, but they should remain owned by their feature and may change with it. This distinction prevents accidental public API growth.

Hooks should follow the architecture categories:

- **Observe:** Listeners react without changing the result.
- **Extend:** Listeners or tagged services add contributions.
- **Replace:** A resolver, provider, or decorator selects behavior; events may participate only when negotiation is needed.

## Technical Specifications
- Use Symfony EventDispatcher for synchronous public and internal lifecycle events.
- Use Symfony Messenger for asynchronous messages, longer-running work, and retryable side effects.
- Name event classes by domain and action, for example `ContentPublishedEvent`, `ThemeResolvedEvent`, or `ModuleEnabledEvent`.
- Keep event payloads small, typed, and immutable where possible.
- Avoid passing full mutable entities to public extension events unless the event explicitly allows mutation.
- Document whether an event allows listeners to mutate a value, stop propagation, add contributions, or only observe.
- Prefer tagged services over mutable events for additive collections where order and priority matter.
- Use listener priority only when ordering is meaningful and documented.
- Keep public events listed in the relevant feature draft and class map.
- Let modules subscribe only to documented public extension events.
- Keep internal events in feature namespaces and avoid advertising them as module hooks.
- Use Messenger messages for indexing, mail, logging enrichment, import processing, backup jobs, and other side effects that can run outside the request.
- Design message handlers to be idempotent where retries are possible.

## Testing & Validation
- Test public event dispatch points.
- Test whether listeners can or cannot mutate payloads according to the event contract.
- Test listener priority only when ordering is documented.
- Test Messenger handlers with retry-safe assumptions.
- Test failure handling for listener exceptions and message handler failures.
- Run `lint:container` after adding subscribers, listeners, handlers, or messenger routing.

## Implementation Notes
- **Decision recorded:** Events are public only when documented as module/theme extension points or stable extension contracts.
- **Decision proposed:** Prefer immutable public event payloads unless mutation is the purpose of the hook.
- **Decision proposed:** Use Messenger for side effects that can be delayed, retried, or processed outside the request.
- **Decision required:** Decide whether public event names should be centralized as constants or rely on class names only.
- **Decision required:** Decide the first Messenger transport setup for local/test/prod environments.
