# Navigation and sitemap builder (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-25
> **Owner**: Core  
> **Purpose:** Draft for managed website navigation, menu publishing, visibility rules, and sitemap generation.  

## Overview
- Defines how editors manage public menus, contextual navigation, footer links, and generated sitemaps.
- Covers menu drafts, menu publishing, entity links, external links, resolver/query links, localization, visibility, and theme rendering.
- Depends on content model, security/ACL, draft/publish workflow, system UI, theme engine, and frontend delivery.
- Keeps public navigation editable without hard-coding menus in templates.

## Outline
A usable CMS needs managed navigation. Menus should be content-aware, versioned, previewable, and renderable by public themes through stable helpers. Editors should be able to create menus, reorder items, link to content entities, add external URLs, hide items by visibility rules, and publish navigation changes safely.

Navigation should not be a special hard-coded template fragment. It should be stored as structured data, validated like other content-adjacent state, and made available to themes, public rendering, API output, and sitemap generation.

## Technical Specifications
- Provide managed menu definitions such as primary, footer, contextual, and system-defined menus.
- Support menu items that reference content entities, external URLs, media/downloads, or controlled resolver/query targets.
- Support nested menu structures with parent/child hierarchy, depth limits, and deterministic sibling ordering.
- Support per-language menu labels and locale-specific menu variants.
- Support visibility rules based on publication state, ACL/capability, language, and optional custom metadata.
- Reuse draft/publish workflow for menu changes where practical.
- Provide admin UI for tree editing, drag/drop or keyboard reordering, item details, preview, and publish review.
- Provide theme-facing helpers or services that return normalized menu trees.
- The first implementation slice exposes `NavigationBuilder` and `studio_navigation()` for active menu trees, currently backed by the seeded `main` menu and anonymous visibility rules.
- `NavigationBuilder::build()` and `studio_navigation()` support `maxDepth` with default `3`, `startLevel` for absolute level slices, and `rootUid` for split menus that render the children of one resolved item.
- `NavigationBuilder::collectItems()` exposes the flat, hook-extended item list before core tree normalization so themes with their own menu builder can reuse core storage and package contributions without using the core render tree.
- Expose `NavigationBuilderEvent` as the package-facing extension hook for adding, removing, or reordering flat navigation items before the builder normalizes parent/child hierarchy, sibling sort order, and depth slices.
- Generate XML/JSON sitemaps from published content and menu state, respecting visibility and ACL rules.
- Allow modules to contribute admin navigation entries through module manifests separately from public website menus.

## Testing & Validation
- Test menu creation, editing, ordering, nesting, publishing, and preview.
- Test entity-linked menu items update when slugs or hierarchy change.
- Test visibility, ACL, and localization behavior.
- Test theme helper output for active/current states and nested children.
- Test default depth limiting, custom depth limiting, absolute level slices, root-item split menus, package item injection, and deterministic sort order.
- Test sitemap output excludes hidden, private, draft, archived, or ACL-restricted content.
- Test keyboard-accessible tree editing once the UI exists.

## Implementation Notes
- **Decision recorded:** Public website navigation needs managed structured data and should not be hard-coded in public templates.
- **Decision recorded:** Public themes should consume navigation through `studio_navigation()` instead of querying menu storage directly.
- **Decision recorded:** `studio_navigation()` defaults to a stable depth of three levels, while templates may request smaller or larger slices through helper arguments.
- **Decision recorded:** Split menus are first-class helper behavior. Templates may render an absolute level with `startLevel` or render only the children below a known item with `rootUid`.
- **Decision recorded:** Themes that need fully custom navigation logic should consume `NavigationBuilder::collectItems()` and build their own tree instead of replacing core storage access or querying menu tables directly.
- **Decision recorded:** Modules and packages may extend resolved navigation through `NavigationBuilderEvent` by contributing `NavigationItem` values with `parentUid` and `sortOrder`; core remains the owner of menu storage, tree normalization, and ACL visibility rules.
- **Decision recorded:** Menu changes should be reviewable and publishable, preferably through the shared draft/publish workflow.
- **Decision recorded:** Public website menus and admin/module navigation are separate concepts.
- **Open:** Decide the first menu types, editor-enforced maximum nesting depth, sitemap formats, active/current item metadata, and whether menu drafts ship with the first navigation slice.
