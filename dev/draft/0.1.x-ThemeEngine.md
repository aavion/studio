# Theme engine (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20  
> **Owner**: Core  
> **Purpose:** Draft for theme resolution, template overrides, asset loading, and local customization behavior.  

## Overview
- Defines how the system chooses template files and assets from core, theme, plugin, and local override sources.
- Covers fallback order, override safety, cache behavior, and rendering integration.
- Depends on core architecture and static/dynamic content decisions.
- Keeps presentation replaceable without hiding Twig, AssetMapper, or Symfony conventions.

## Outline
The theme engine should resolve presentation files without turning rendering into a separate framework. Twig should remain the template layer, AssetMapper/importmap should remain the default asset layer, and themes should provide a documented fallback and override structure.

The core should ship safe default templates. A selected theme may override public-facing templates and provide assets. Local project overrides may sit above the selected theme for site-specific customization. Plugin modules may contribute template candidates, blocks, assets, or Twig extensions only through documented extension points.

Themes may also ship PHP classes under their own namespace for theme-specific Twig functions, Twig extensions, event subscribers, or other documented extension hooks. Theme PHP integration must still be explicit, manifest-driven, and validated before activation.

Dynamic schema Twig stored in the database is not part of theme template resolution. The theme provides the outer page layout and generic fieldset fallback renderer; schema rendering may replace or extend only the inner content block for that schema.

Theme resolution should be deterministic. When several sources provide a template or asset, the resolver should explain which source won and why. This is important for debugging, updates, self-update safety, and LLM-assisted review.

Theme activation, deactivation, update, or override changes may change Tailwind class usage and AssetMapper inputs. The production-safe workflow should trigger an explicit asset rebuild after theme lifecycle changes: first run the Tailwind build, then compile the asset map. A local file watcher may still be useful during development, but administrative theme changes should use a deterministic rebuild action with clear logs and failure handling.

Discovered themes should not become active automatically. Discovery may validate metadata and show the theme as available, but activation must be an explicit admin action. This guarantees that manifest validation, compatibility checks, asset rebuilds, cache invalidation, diagnostics, and action logs happen in the right order before the theme affects rendering.

Theme activation should fail safely. If validation, cache invalidation, Tailwind build, or AssetMapper compilation fails, the system should restore the previous active theme option where practical and show the failure through the operational action log. This keeps the lifecycle simple without introducing a separate staged asset compiler.

Theme dependency resolution is deferred to the theme installer and activation workflow. The shared core package planner should not infer theme dependencies or compatibility maps. A later theme resolver should define how theme manifests express required core versions, required modules, conflicts, optional suggestions, provided capabilities, and update compatibility before an administrator can activate or update a theme.

## Technical Specifications
- Use Twig for templates and keep template names readable.
- Use AssetMapper and importmap entrypoints for theme and page assets where possible.
- Use `symfonycasts/tailwind-bundle` for Tailwind builds already present in the project.
- Define a theme manifest using the shared `.manifest` style with `THEME_` keys.
- Use the package layout `themes/<theme-name>/` with `.manifest`, `src/`, `templates/`, `assets/`, and optional `translations/`.
- Let themes define their own PHP namespace for classes in `src/`.
- Allow theme classes to register with documented event hooks or tagged services only after manifest validation.
- Suggested theme resolution order:
  1. Local project override.
  2. Active theme.
  3. Plugin module contribution where allowed.
  4. Core default template.
- Define whether plugin contributions are allowed per template area, for example public page, editor widget, form field, navigation item, or content block.
- Keep admin templates more restrictive than public-facing templates.
- Do not allow admin template overrides in early releases. Keep the option open for a later explicit feature.
- Let theme overrides follow the original folder structure. If a file exists in the active theme at the corresponding path, it replaces the matching base file for allowed public template areas.
- Use a resolver service for template candidates and asset candidates.
- Use tagged services for additive theme contributions such as content block renderers, editor widgets, or navigation renderers.
- Use service decoration or configuration only for explicit replacement points such as a custom template resolver.
- Cache resolved theme metadata and invalidate it when theme configuration, manifests, or override files change.
- Keep theme dependency and compatibility checks in the theme installer/activation workflow rather than in generic package planning.
- Discover newly extracted themes as inactive/available until an administrator explicitly activates them.
- Require explicit activation before a discovered theme contributes templates, assets, PHP classes, Twig extensions, or event subscribers.
- Trigger an explicit asset rebuild after theme activation, deactivation, update, or relevant override changes.
- Roll back to the previous active theme option when activation fails before the new theme can be safely finalized.
- Run `php bin/console tailwind:build` before `php bin/console asset-map:compile` for theme lifecycle rebuilds.
- Treat theme templates, CSS sources, JavaScript sources, imported assets, and manifest-declared assets as rebuild inputs.
- Use a development watcher only as a local convenience; do not rely on watchers for production/admin lifecycle changes.
- Provide diagnostics for resolved templates and assets in development mode.
- Keep theme assets namespaced to avoid collisions.
- Keep database-backed schema Twig outside the theme file fallback order.
- Package themes so they can be extracted as subdirectories below `themes/`, where their manifest can be discovered before PHP classes, templates, assets, and overrides are loaded.

## Testing & Validation
- Test fallback order for local, theme, plugin, and core templates.
- Test folder-structure-based overrides replace only allowed base files.
- Test theme PHP classes are loaded only after manifest validation and only through documented hooks.
- Test missing templates fall back safely or produce actionable developer errors.
- Test that plugin contributions are accepted only for allowed template areas.
- Test active theme manifest validation.
- Test theme dependency, conflict, and compatibility diagnostics once the theme installer defines the manifest keys.
- Test newly discovered themes remain inactive until explicitly activated.
- Test inactive themes do not contribute templates, assets, classes, extensions, or event subscribers.
- Test that theme resolution does not override database-backed schema Twig behavior.
- Test theme activation/update triggers the asset rebuild workflow.
- Test failed theme activation restores the previous active theme option and reports the failure.
- Test asset rebuild failures leave the previous active assets usable where practical and report actionable errors.
- Run `php bin/console tailwind:build` after Tailwind-related changes.
- Run `php bin/console asset-map:compile` after AssetMapper/importmap changes.
- Render representative public routes with `.codex/render.php /<route>`.

## Implementation Notes
- **Decision recorded:** Use Twig and AssetMapper as the first theme engine foundation.
- **Decision recorded:** Use `.manifest` files with `THEME_` keys for theme metadata.
- **Decision recorded:** Theme packages live under `themes/<theme-name>/` and may contain `.manifest`, `src/`, `templates/`, `assets/`, and optional `translations/`.
- **Decision recorded:** Themes may ship PHP classes under their own namespace and integrate through documented event hooks, tagged services, or Twig extensions after manifest validation.
- **Decision recorded:** Make local project overrides stronger than active theme files.
- **Decision recorded:** Database-backed schema Twig is owned by content schema rendering, not the theme engine. Themes provide outer layout and generic fallback rendering.
- **Decision recorded:** Theme file overrides follow the original folder structure and replace the corresponding base file only in allowed public template areas.
- **Decision recorded:** Admin template overrides remain possible later but are not supported in early releases.
- **Decision recorded:** Theme release packages are extracted as subdirectories below `themes/`, then discovered through their manifest before classes, templates, assets, or overrides are loaded.
- **Decision recorded:** Discovered themes are inactive by default and require explicit activation before they can affect rendering or register contributions.
- **Decision recorded:** Theme dependency maps are intentionally deferred to the theme installer and activation workflow; generic Core package planning remains dependency-neutral.
- **Decision recorded:** Failed theme activation rolls back to the previous active theme option where practical and reports the error through the operational action log.
- **Decision recorded:** Theme lifecycle changes trigger an explicit Tailwind build followed by AssetMapper compilation. File watchers are only a development convenience.
