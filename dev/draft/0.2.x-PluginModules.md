# Plugin modules (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for installing, discovering, configuring, and safely extending the CMS through plugin modules.

## Overview
- Defines how plugin modules add or replace functionality.
- Covers module manifests, services, routes, assets, migrations, permissions, and lifecycle hooks.
- Depends on the core architecture, event hooks, and theme engine drafts.
- Defines the contract between the CMS core and optional first-party or third-party packages.

## Outline
Plugin modules should extend the CMS without forcing the core to anticipate every future use case. A module may contribute routes, services, templates, assets, field types, editor actions, API resources, permissions, migrations, event subscribers, message handlers, or replaceable providers, but only through documented extension points.

The first module system should be intentionally conservative. Discovery, metadata validation, compatibility checks, enable/disable state, and dependency ordering should be implemented before modules can make deep runtime changes. Modules should be easy to inspect from their manifest, service definitions, migrations, tests, and class map references.

The module lifecycle should prefer Symfony-native behavior. A module should integrate through service registration, tagged services, event subscribers, message handlers, route imports, Twig paths, AssetMapper assets, Doctrine migrations, and security voters where applicable. Custom loading logic should stay narrow and focused on discovery, validation, and lifecycle orchestration.

## Technical Specifications
- Use `.manifest`-style metadata with `MODULE_` keys.
- Suggested required keys:
  - `MODULE_NAME`
  - `MODULE_VERSION`
  - `MODULE_CHANNEL`
  - `MODULE_SOURCE`
  - `MODULE_COMPATIBILITY`
  - `MODULE_ENTRYPOINT`
- Suggested optional keys:
  - `MODULE_DESCRIPTION`
  - `MODULE_DEPENDS`
  - `MODULE_CONFLICTS`
  - `MODULE_MIGRATIONS`
  - `MODULE_ROUTES`
  - `MODULE_ASSETS`
  - `MODULE_PERMISSIONS`
  - `MODULE_AUTHOR`
- Validate manifests before registering module contributions.
- Store enabled/disabled module state in application configuration or database-backed module state once persistence exists.
- Discover module packages from a predictable directory or configured package registry.
- Keep first-party modules and third-party modules under the same lifecycle rules, but allow stricter trust defaults for third-party packages.
- Use tagged services for additive contributions.
- Use documented contracts/resolvers for replacement contributions.
- Use EventDispatcher and Messenger only for documented public module hooks.
- Let modules declare migration paths or namespaces, then execute them through a core-owned migration workflow.
- Let modules declare route resources only after compatibility and enabled state are validated.
- Keep module assets namespaced.
- Keep module permissions declared and mapped through the security draft before routes or admin UI rely on them.
- Provide diagnostics for invalid manifests, missing dependencies, conflicts, disabled modules, and failed contributions.

## Testing & Validation
- Test manifest parsing and validation.
- Test module discovery with valid, invalid, disabled, missing-dependency, and conflicting modules.
- Test additive tagged service contributions.
- Test replacement provider selection and fallback behavior.
- Test route, asset, migration, and permission declarations separately.
- Test that disabled modules do not contribute routes, services, templates, or migrations.
- Run `lint:container` after service integration changes.
- Add integration fixtures for one minimal first-party module and one intentionally invalid module.

## Implementation Notes
- **Decision proposed:** Treat modules as Symfony-integrated packages with a lightweight manifest, not as a separate runtime framework.
- **Decision proposed:** Require manifest validation before any contribution is registered.
- **Decision proposed:** Use one lifecycle for first-party and third-party modules, with stricter trust and review rules for third-party modules.
- **Decision required:** Decide the module install directory and package layout.
- **Decision required:** Decide whether disabled module state lives in config files first or database state first.
- **Decision required:** Decide whether module route registration happens at cache warmup only or can change dynamically in dev mode.
