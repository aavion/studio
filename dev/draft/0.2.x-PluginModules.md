# Plugin modules (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for installing, discovering, configuring, and safely extending the CMS through plugin modules.  

## Overview
- Defines how plugin modules add or replace functionality.
- Covers module manifests, services, routes, assets, migrations, permissions, and lifecycle hooks.
- Depends on the core architecture, event hooks, and theme engine drafts.
- Defines the contract between the CMS core and optional first-party or third-party packages.

## Outline
Plugin modules should extend the CMS without forcing the core to anticipate every future use case. A module may contribute routes, services, templates, assets, field types, editor actions, API resources, permissions, migrations, event subscribers, message handlers, or replaceable providers, but only through documented extension points.

Replaceable provider modules are a central module use case. Captcha providers are the first concrete example: the core exposes a resolver and configuration option, while modules such as IconCaptcha contribute the actual provider service, assets, templates, translations, and validation behavior. If a provider module is disabled, the resolver must fall back according to core configuration rather than leaving workflows broken.

The first module system should be intentionally conservative. Discovery, metadata validation, compatibility checks, enable/disable state, and dependency ordering should be implemented before modules can make deep runtime changes. Modules should be easy to inspect from their manifest, service definitions, migrations, tests, and class map references.

The module lifecycle should prefer Symfony-native behavior. A module should integrate through service registration, tagged services, event subscribers, message handlers, route imports, Twig paths, AssetMapper assets, Doctrine migrations, and security voters where applicable. Custom loading logic should stay narrow and focused on discovery, validation, and lifecycle orchestration.

Module dependency resolution should be implemented in the module installer and lifecycle workflow, not in the shared package planner. The resolver should later define how manifests express hard requirements, conflicts, optional suggestions, provided capabilities, compatible core versions, compatible module versions, and update constraints. Dependency checks should be able to compare installed modules, disabled modules, available staged packages, and administrator-selected packages before an enable, update, or uninstall action runs.

Modules must also define how they are removed. Because modules may provide migrations and module-owned tables, uninstall or remove workflows must avoid data leftovers where possible and must ask for explicit confirmation before deleting module-owned data.

Module lifecycle changes may add or remove Twig templates, Tailwind class usage, JavaScript entrypoints, imported CSS, or static assets. Enabling, disabling, installing, updating, or uninstalling a module with frontend contributions should trigger a controlled asset rebuild instead of relying on a filesystem watcher. The rebuild should run through the same operational action-log pattern as other admin lifecycle operations.

Discovered modules should be registered as available but inactive by default. Discovery may parse manifests, validate compatibility, and show diagnostics, but modules must not contribute services, routes, templates, assets, migrations, permissions, providers, or event subscribers until an administrator explicitly enables them. This keeps activation auditable and guarantees that rebuild and lifecycle workflows are not skipped.

Module enablement should fail safely. If validation, migration checks, contribution registration, cache invalidation, Tailwind build, or AssetMapper compilation fails, the system should restore the previous enabled/disabled state where practical and show the failure through the operational action log. This is simpler than a staged compiler model and matches the expectation that lifecycle operations are explicit and recoverable.

## Technical Specifications
- Use `.manifest`-style metadata with `MODULE_` keys.
- Use the package layout `modules/<module-name>/` with `.manifest`, `src/`, `config/`, `templates/`, `assets/`, `translations/`, and `migrations/` where needed.
- Suggested required keys:
  - `MODULE_NAME`
  - `MODULE_VERSION`
  - `MODULE_CHANNEL`
  - `MODULE_SOURCE`
  - `MODULE_COMPATIBILITY`
  - `MODULE_ENTRYPOINT`
- Suggested optional keys:
  - `MODULE_DESCRIPTION`
  - `MODULE_DEPENDS`
  - `MODULE_CONFLICTS`
  - `MODULE_MIGRATIONS`
  - `MODULE_ROUTES`
  - `MODULE_ASSETS`
  - `MODULE_PERMISSIONS`
  - `MODULE_AUTHOR`
- Validate manifests before registering module contributions.
- Resolve module dependencies, conflicts, provided capabilities, optional suggestions, and compatibility constraints before enablement, update, or uninstall workflows mutate state.
- Store enabled/disabled module state in application configuration or database-backed module state once persistence exists.
- Discover module packages from a predictable directory or configured package registry.
- Mark newly discovered modules as inactive/available by default.
- Require explicit admin enablement before a discovered module contributes services, routes, templates, assets, migrations, permissions, providers, event subscribers, or message handlers.
- Keep first-party modules and third-party modules under the same lifecycle rules, but allow stricter trust defaults for third-party packages.
- Use tagged services for additive contributions.
- Use documented contracts/resolvers for replacement contributions.
- Support replaceable provider modules, for example captcha providers, through documented provider contracts, tagged services, and explicit resolver selection.
- Keep provider-module assets, templates, translations, and configuration namespaced to the module package.
- Provide deterministic fallback behavior when a selected provider is disabled, missing, or uninstalled.
- Use EventDispatcher and Messenger only for documented public module hooks.
- Let modules declare migration paths or namespaces, then execute them through a core-owned migration workflow.
- Let modules declare route resources only after compatibility and enabled state are validated.
- Register module routes during cache warmup or an explicit rebuild flow. Avoid magical runtime route changes.
- Store disabled/enabled module state in database-backed module state once persistence exists. Configuration may provide initial defaults.
- Keep module assets namespaced.
- Let modules declare frontend contributions that require asset rebuilds, including templates, Tailwind/CSS sources, JavaScript sources, importmap entries, and static assets.
- Trigger `php bin/console tailwind:build` and then `php bin/console asset-map:compile` after module install, enable, disable, update, or uninstall when frontend contributions changed.
- Roll back to the previous module enabled/disabled state when enablement or disablement fails before it can be safely finalized.
- Use explicit rebuild actions for admin/module lifecycle changes. File watchers may support local development but must not be required for production correctness.
- Provide a remove/uninstall routine for modules that can reverse module registration and optionally remove module-owned data through confirmed migrations or cleanup steps.
- Keep module permissions declared and mapped through the security draft before routes or admin UI rely on them.
- Provide diagnostics for invalid manifests, missing dependencies, conflicts, disabled modules, and failed contributions.

## Testing & Validation
- Test manifest parsing and validation.
- Test module discovery with valid, invalid, disabled, missing-dependency, and conflicting modules.
- Test dependency resolution against installed modules, disabled modules, staged packages, conflicts, suggestions, and provided capabilities once the module installer defines the manifest keys.
- Test newly discovered modules remain inactive until explicitly enabled.
- Test inactive modules do not contribute services, routes, templates, assets, migrations, permissions, providers, subscribers, or handlers.
- Test additive tagged service contributions.
- Test replacement provider selection and fallback behavior.
- Test provider modules can contribute namespaced assets, templates, translations, and services without leaking into core package structure.
- Test selected provider fallback when a provider module is disabled or unavailable.
- Test route, asset, migration, and permission declarations separately.
- Test module lifecycle changes trigger asset rebuilds when frontend contributions changed.
- Test failed module enablement or disablement restores the previous state and reports the failure.
- Test that disabled modules do not contribute routes, services, templates, or migrations.
- Test module remove/uninstall flows with and without module-owned data deletion.
- Run `lint:container` after service integration changes.
- Add integration fixtures for one minimal first-party module and one intentionally invalid module.

## Implementation Notes
- **Decision recorded:** Treat modules as Symfony-integrated packages with a lightweight manifest, not as a separate runtime framework.
- **Decision recorded:** Require manifest validation before any contribution is registered.
- **Decision recorded:** Module dependency maps and compatibility checks belong to the module installer/lifecycle workflow. The shared Core package planner remains dependency-neutral.
- **Decision recorded:** Use one lifecycle for first-party and third-party modules, with stricter trust and review rules for third-party modules.
- **Decision recorded:** Module packages live under `modules/<module-name>/` and may contain `.manifest`, `src/`, `config/`, `templates/`, `assets/`, `translations/`, and `migrations/`.
- **Decision recorded:** Newly discovered modules are inactive by default and require explicit admin enablement before contributing anything to the runtime.
- **Decision recorded:** Disabled/enabled module state should live in database-backed module state once persistence exists, with configuration used only for initial defaults.
- **Decision recorded:** Failed module lifecycle operations roll back to the previous enabled/disabled state where practical and report the error through the operational action log.
- **Decision recorded:** Module route registration happens during cache warmup or an explicit rebuild flow, not through magical runtime route changes.
- **Decision recorded:** Modules need a remove/uninstall routine that can safely remove registrations and optionally clean up module-owned data with explicit confirmation.
- **Decision recorded:** Replaceable providers such as captcha providers are first-class module contributions exposed through core-owned resolver contracts and explicit configuration.
- **Decision recorded:** Provider modules own their assets, templates, translations, and services. Core owns provider selection and fallback behavior.
- **Decision recorded:** Module lifecycle changes with frontend contributions trigger an explicit Tailwind build followed by AssetMapper compilation. Watchers are development-only convenience tooling.
