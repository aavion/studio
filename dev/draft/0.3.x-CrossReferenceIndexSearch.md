# Cross-reference index and search (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for automatic cross-reference resolution, content indexing, and search behavior.  

## Overview
- Defines how content references are detected, stored, resolved, and displayed.
- Covers search indexing, relationship discovery, and deterministic resolver indexing.
- Depends on the content model, schema-driven fields, and import/export format decisions.
- Creates a foundation for broken-link detection, related content, search, editor autocomplete, and efficient fieldset assembly.

## Outline
The CMS should understand relationships between content items instead of treating every page as isolated text. References may come from explicit content reference fields, links in rich text, media references, taxonomy-like fields, imports, module data, or future generated suggestions.

The first cross-reference system should focus on deterministic references: content UIDs, slugs, URLs, media IDs, field identifiers, language variants, generic variants, and field-level references. A resolver engine should start with explicit reference links, reference fields, controlled query fields, and title-based reference suggestions.

The resolver should make project graphs usable for human and LLM-assisted workflows. For example, a story project may contain separate entities for scenes, characters, memories, locations, timeline events, and lore notes. Reference fields and query fields should let the system collect the relevant context around the current scene without duplicating that context inside the scene itself. Inline resolver syntax can later expose the same capability inside Markdown or rich text fields.

Internal authoring syntax and collaboration export syntax may differ. Editors can use compact dynamic tokens, while LLM-oriented exports can expand those tokens into explicit tagged spans such as `[ref:character/bernd]Bernd[/ref]` or `[query:scene-context?limit=5]...[/query]`. Ref-links and query tokens must also be able to target specific fields, for example a compact token shaped like `[[ref:slug{~variant}/field]]` once the exact grammar is defined. This gives an external assistant enough information to know where additional context can be requested without forcing the assistant to resolve the reference by itself.

Search should begin with a small database-backed index table if practical, then allow replacement with a dedicated adapter later. The architecture should make search adapters replaceable without coupling content storage to one search engine. External URL checks are lower priority than internal reference resolution; external links may initially be marked and decorated without crawling their content.

The first resolver index should be built in two passes. The first pass collects all candidate entities, fields, stable identifiers, slugs, titles, variants, and raw reference-bearing values. The second pass resolves references against that complete map, records outgoing references, derives incoming references, and collects resolver errors. This avoids order-dependent behavior and makes rebuild reports deterministic.

The resolver index must stay lean. It should not duplicate all content in a resolved JSON payload or become the primary frontend content source. Content should be loaded from the database and resolved at runtime where practical. The index should store lookup and graph metadata that helps the system find entities, variants, fields, relationships, broken references, and query targets quickly. This database-backed index should also help the database/query layer assemble variable fieldsets efficiently without scanning all field values for every request.

Resolver rebuilds should produce an inspectable report. The report should include counts, broken references, ambiguous references, cycle warnings, stale targets, and ACL-restricted references where the actor is allowed to see those diagnostics. Reports should be usable from the admin UI and CLI so indexing problems can be reviewed before publishing, exporting, or relying on LLM context bundles.

## Technical Specifications
- Define reference records with source, target, reference type, field/path, and status.
- Build the first resolver index in two passes: collect raw reference sources first, then resolve against the complete target map.
- Support explicit reference links that point to entities, fields, variants, or controlled content-query outputs.
- Allow resolver tokens to target specific fields, for example an eventual form similar to `[[ref:slug{~variant}/field]]`.
- Index references created by schema reference fields, including single-target and multi-target relationships.
- Index controlled query field definitions as dynamic reference sources and distinguish them from materialized direct links.
- Support derived inverse relationship lookups, for example finding all content items that reference a given character or location.
- Define a small shortcode or resolver-token format for inline references in Markdown or rich text fields.
- Keep shortcode parsing deterministic and validated before expanding into rendered output, exports, or LLM context.
- Keep internal resolver tokens dynamic and non-destructive, for example compact authoring tokens that can be re-resolved as content changes.
- Allow export formatters to render internal resolver tokens as explicit tagged spans with visible labels and machine-readable reference or query targets for LLM collaboration.
- Allow import parsers to normalize supported tagged spans back into internal resolver tokens after validation, so round trips do not hard-code resolved content into stored fields.
- Reject or flag malformed, ambiguous, forbidden, or ACL-restricted tagged spans during import validation.
- Start title-based reference suggestions with content titles before expanding to broader term extraction.
- Let resolver suggestions begin with exact or near-exact title matches.
- Keep resolver-generated links reviewable or reversible so automatic suggestions do not silently corrupt authored content.
- Include language and generic variant context in reference records when the reference is variant-specific.
- Include field identifiers when references originate from schema-driven field values.
- Track broken, unpublished, moved, and external references distinctly.
- Track outgoing references and derived incoming references as first-class graph data.
- Define resolver error codes such as `not_found`, `field_not_found`, `empty`, `ambiguous`, `acl_restricted`, and `cycle`.
- Protect recursive resolution and context gathering with both maximum depth and stack-based cycle detection.
- Respect content visibility and ACL restrictions when returning search results or related-content suggestions.
- Update references after content save, publish, import, delete, restore, and schema migration operations.
- Use Messenger for rebuilds or expensive indexing work.
- Use events for lifecycle notification such as content indexed or broken reference detected when documented.
- Define a `SearchAdapter`-style replacement point before adopting external search.
- Use small custom database-backed index tables as the first search/reference index implementation.
- Store only indexable lookup and graph metadata in the resolver index, not full resolved content payloads.
- Load content from normalized database tables for rendering and runtime resolution where practical.
- Update the resolver index asynchronously after content, schema, import, publish, delete, or restore changes where practical.
- Support rebuild commands for references and search indexes.
- Let rebuild commands support dry-run/report mode before persisting a rebuilt index.
- Allow external links to be configured to open in a new window and be decorated with an external-link icon.
- Make import/export preserve stable content identifiers and reference intent where possible.
- Provide context-gathering APIs or services that can walk deterministic references, controlled query results, and approved resolver suggestions from a starting content item.
- Provide admin diagnostics for broken references and stale indexes.

## Testing & Validation
- Test explicit content reference fields.
- Test field-targeted resolver references once resolver-token syntax exists.
- Test single-target and multi-target reference fields.
- Test derived inverse lookups from indexed references.
- Test controlled query fields as dynamic reference sources.
- Test two-pass indexing stays deterministic regardless of content order.
- Test outgoing and incoming reference graph generation.
- Test resolver error code reporting.
- Test max-depth and stack-based cycle protection.
- Test inline resolver-token parsing once shortcode syntax exists.
- Test export expansion from internal resolver tokens to LLM-readable tagged spans.
- Test import normalization from supported tagged spans back to internal resolver tokens.
- Test references for language-specific and generic-variant-specific field values.
- Test field identifier tracking in reference records.
- Test references extracted from rich text or markdown once those editors exist.
- Test broken, moved, unpublished, and deleted targets.
- Test ACL-restricted content is not returned in search or related-content results for unauthorized users.
- Test index rebuilds are idempotent.
- Test dry-run rebuild reports do not persist index changes.
- Test resolver index storage remains a lean metadata/index structure and does not duplicate full resolved content.
- Test runtime resolution loads current content from database-backed content services.
- Test search adapter replacement and default adapter behavior.
- Test title-based reference suggestions.
- Test context gathering from a starting entity through explicit references and query fields.
- Test explicit reference links to entities, fields, and controlled query outputs.
- Test external-link decoration behavior when configured.
- Test import/export round trips preserve references.
- Test Messenger indexing handlers where asynchronous rebuild is used.

## Implementation Notes
- **Decision recorded:** Start with deterministic reference indexing.
- **Decision recorded:** Build the resolver index in two passes: collect all raw sources and targets first, then resolve references against the complete map.
- **Decision recorded:** Deterministic reference records should preserve content UID, field identifier, language, and generic variant context when available.
- **Decision recorded:** The resolver graph tracks both outgoing and incoming references.
- **Decision recorded:** Resolver diagnostics should use explicit error codes and report broken, ambiguous, empty, ACL-restricted, and cyclic references.
- **Decision recorded:** Recursive resolution and context gathering require max-depth and stack-based cycle protection.
- **Decision recorded:** Search and related-content output must respect content visibility and ACL restrictions.
- **Decision recorded:** Keep search adapter replaceable from the start, but use small custom database-backed index tables as the first default implementation.
- **Decision recorded:** Resolver indexes are lean metadata/index structures, not duplicated resolved content stores. Runtime rendering should load content from the database and resolve references on demand where practical.
- **Decision recorded:** The resolver index may be updated asynchronously and should help locate entities, variants, fields, relationship edges, query targets, and fieldset assembly inputs efficiently.
- **Decision recorded:** Start resolver behavior with explicit reference links and title-based suggestions.
- **Decision recorded:** Reference fields, controlled query fields, and inline resolver tokens should all feed the same cross-reference and context-gathering model.
- **Decision recorded:** The first resolver engine should support deterministic context gathering from a starting content entity through direct references, inverse references, and controlled query results.
- **Decision recorded:** Internal resolver tokens should remain dynamic and non-destructive. LLM-oriented exports may expand them into tagged spans such as `[ref:target]Label[/ref]` or `[query:target]Rendered result[/query]`, and imports may normalize those spans back into internal tokens after validation.
- **Decision recorded:** Ref-links and query tokens must support field-level targets in addition to entity and variant targets.
- **Deferred:** Define the exact internal resolver-token syntax and exported tagged-span grammar during implementation planning, after required resolver capabilities are known. This must cover field targeting, resolution depth, loop protection, query syntax, allowed functions, validation behavior, ACL handling, and export/import normalization rules.
- **Decision recorded:** Use Messenger for expensive rebuilds.
- **Decision recorded:** Resolver rebuilds should support dry-run/report mode before persisting index changes.
- **Decision recorded:** External URL checks are lower priority. Initial behavior may focus on opening external links in a new window and decorating them with an icon rather than crawling external content.
