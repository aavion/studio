# Core architecture (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-22
> **Owner**: Core  
> **Purpose:** Draft for the base application boundaries, modular structure, and extension strategy before feature implementation.

## Overview
- Defines the application layers and ownership boundaries for the CMS core.
- Establishes how core services, modules, themes, content structures, events, and infrastructure tooling should fit together.
- Provides the foundation for all later feature drafts.
- Favors Symfony-native structure and extension mechanisms over custom framework code.
- Keeps future plugin, theme, editor, API, and release features possible without broad rewrites.

## Outline
aavion.studio should be built as a Symfony application first and a CMS framework second. The core should define stable application boundaries, shared contracts, and common infrastructure, while concrete features remain small enough to understand, test, replace, or remove independently.

The first public development phase should avoid a large custom platform layer. Symfony already provides the application model for routing, services, forms, validation, events, security, message handling, configuration, translation, assets, and persistence. Core architecture should therefore use Symfony mechanisms directly unless a custom contract is needed to make plugin modules, themes, or content workflows safely replaceable.

The system should be organized around small vertical feature slices. A feature slice may contain routes/controllers, services, entities or DTOs, form types, validators, Twig templates, translations, tests, and documentation. Each slice should remain discoverable through predictable namespaces, draft links, class map entries, and worklog notes.

Plugin modules should not require the core to know every future feature in advance. Instead, the core should expose documented extension points in three categories:

- **Observe:** A module reacts to a lifecycle event without changing the result.
- **Extend:** A module contributes additional behavior through a hook, tagged service, or configuration.
- **Replace:** A module replaces a selected strategy through an explicit contract, resolver, service decoration, or configuration.

Events are part of the architecture, but they should not become the only abstraction. EventDispatcher should model synchronous lifecycle boundaries and extension hooks. Messenger should handle asynchronous work and delayed side effects. Replacement behavior should be explicit and discoverable through contracts and resolvers rather than hidden inside arbitrary event listeners.

The architecture should be context-friendly. Future contributors and coding agents should be able to inspect a feature by reading its draft, its namespace, its tests, and its class map entries without loading unrelated modules. Large rewrites should be avoided by making extension boundaries explicit before implementation, especially around content modeling, theme resolution, plugin modules, security, editor workflows, and import/export.

## Technical Specifications
- Use the `App\` namespace for core application code.
- Keep Symfony conventions recognizable:
  - Controllers in `src/Controller/`.
  - Entities in `src/Entity/`.
  - Repositories in `src/Repository/`.
  - Feature services in small namespaces under `src/`.
  - Twig templates in `templates/`.
  - Stimulus controllers in `assets/controllers/`.
  - Configuration in `config/`.
  - Tests mirroring production namespaces under `tests/`.
- Prefer constructor injection and autowiring through `config/services.yaml`.
- Prefer Symfony configuration, tagged services, service decoration, EventDispatcher, Messenger, voters, form types, validators, and Twig extension points before adding custom registries or loaders.
- Define explicit contracts only for behavior that must be replaceable or contributed by modules.
- Keep contracts narrow and behavior-oriented. Avoid broad manager interfaces that collect unrelated responsibilities.
- Use priority-based resolver services for replaceable strategies such as captcha providers, storage adapters, search adapters, export formatters, theme resolvers, or editor integrations.
- Use tagged service collections for additive behavior such as editor actions, export formats, navigation entries, form extensions, content field types, or template candidates.
- Use Symfony events for lifecycle notification and controlled extension hooks, for example content saved, content published, module enabled, theme resolved, export prepared, import validated, or backup completed.
- Use Messenger for asynchronous side effects such as search indexing, mail delivery, statistics enrichment, backup jobs, import processing, and longer-running maintenance tasks.
- Keep user-facing recoverable flows explicit. Validation failures should preserve input where possible and return actionable feedback rather than relying on generic exceptions.

### Proposed namespace groups

The exact namespace layout should evolve as features become real, but the first implementation phase should start from a small predictable set:

| Namespace | Purpose |
|-----------|---------|
| `App\Core\` | Shared contracts, value objects, result objects, and cross-feature infrastructure. |
| `App\Content\` | Static and dynamic content model, content services, field schemas, and rendering coordination. |
| `App\Theme\` | Theme discovery, template resolution, asset resolution, and override handling. |
| `App\Module\` | Plugin module manifests, discovery, lifecycle, dependency checks, and module configuration. |
| `App\Security\` | ACL, voters, captcha contracts, rate-limit helpers, and security extension points. |
| `App\Editor\` | Administrative editor workflows, previews, diffs, and editing-specific integrations. |
| `App\Integration\` | Import/export, API-facing adapters, and collaboration exchange formats. |
| `App\Operations\` | Backup, restore, setup, release, update, logging, and maintenance workflows. |

Namespaces may grow in scope as long as their internal structure stays modular. A larger namespace is acceptable when it contains small services, contracts, DTOs, tests, and documentation that remain easy to inspect independently.

### Manifest format

Application, plugin module, and theme metadata should use a lightweight `.manifest`-style format based on `KEY=VALUE` pairs. The root `.manifest` already uses this structure for update metadata:

- `APP_VERSION`
- `APP_DATE`
- `APP_CHANNEL`
- `APP_SOURCE`

The same pattern should be reused for modules and themes where practical. It keeps metadata easy to read, cheap to parse, friendly to release tooling, and close to Symfony's existing environment-file conventions. Because `symfony/dotenv` is already part of the project, manifest parsing can use Symfony-native parsing behavior or a deliberately small parser if stricter manifest-specific validation is needed.

Manifest files should stay simple:

- Use deterministic uppercase keys with package-specific prefixes such as `APP_`, `MODULE_`, or `THEME_`.
- Store only metadata, discovery hints, compatibility requirements, update sources, channels, branches, and declared contributions.
- Do not store secrets or environment-specific credentials.
- Avoid nested structures. When lists are required, prefer simple comma-separated values or repeated documented keys.
- Validate required keys and unknown critical values before a module or theme is registered.
- Keep parsing separate from domain validation. The shared manifest parser should understand only syntax and duplicate keys; required keys and closed allowed-key sets belong to per-feature manifest specifications. Prefer namespace-based specs where callers provide a namespace such as `THEME`, short allowed keys such as `VERSION` and `AUTHOR`, and short required keys such as `NAME` and `VERSION`; the spec expands those to full manifest keys like `THEME_VERSION`.

### Extension point rules

- Every extension point must be documented in the relevant feature draft before implementation.
- Every extension point must state whether it is `Observe`, `Extend`, or `Replace`.
- Replacement points must have one selected default implementation in core.
- Replacement points must define how selection works for that specific extension point. Selection may use configuration, priority, service decoration, an event-based negotiation step, or a combination, but the final behavior must be explicit and testable.
- Module-provided behavior must fail safely. If a module contribution is invalid or unavailable, the system should log useful context and fall back where possible.
- Extension points should remain stable only after they are intentionally marked as stable. Before `1.0.0`, obsolete contracts may be removed when drafts, callers, tests, and documentation are updated together.
- Event-based replacement should be used only when a feature genuinely needs several listeners to negotiate or modify a result. Simple one-active-provider replacement should prefer a resolver or configuration-selected provider because that is easier to trace and review.
- An event is public only when it is documented as a module or theme extension point, marked as `Observe`, `Extend`, or `Replace`, or listed as a stable extension contract. Undocumented events are internal lifecycle events and may change with their owning feature.

### Module migrations

Plugin modules may provide migrations before `1.0.0`, but the mechanism should be consistent from the start. Module migrations should be discovered through module metadata and executed through a single core-owned migration workflow rather than each module running ad-hoc database changes.

The core content model may use variable fieldsets for flexible content structures, but module-owned domain data should prefer module-owned tables when it is more explicit, queryable, and maintainable. Modules may use their own table namespace or prefix instead of storing unrelated domain data inside generic shared fieldset tables. Shared fieldsets should be used for content-like extension data, not as a substitute for clear module persistence boundaries.

The first migration design should prefer Symfony and Doctrine conventions:

- Keep core migrations in the existing application migration flow.
- Let modules declare migration paths or migration namespaces in their manifest metadata.
- Run module migrations through controlled console commands with dry-run and confirmation behavior where applicable.
- Track which module migrations have been applied.
- Validate that a module is compatible before applying its migrations.
- Prefer explicit module-owned tables for module domain data when a module needs durable structured storage.
- Allow breaking migration strategy changes before `1.0.0` when drafts, code, tests, and documentation are updated together.

### API boundary

The first API scope should be content interaction only. API endpoints should expose content retrieval and content-oriented operations defined by the content and API drafts. Internal process control, administrative automation, module lifecycle operations, update workflows, backup/restore, and other operational controls should stay out of the initial API surface unless a later draft explicitly adds them.

### Configuration model

Global configuration should be managed through the admin panel and stored in a database-backed configuration table once persistence exists. Global configuration is administrator-only: reading and writing global settings requires the `Administrators` ACL group unless a later draft explicitly exposes a value elsewhere.

Editor-facing preferences and global administrator configuration should stay logically separate so ACLs can be scoped cleanly. User-specific settings such as scoped API tokens belong to the user/profile context, not the global configuration table. Project-specific overrides such as a project or subpage using another theme should be stored as project/content fields in the project hub or relevant content model rather than as separate global config keys.

Configuration precedence should stay simple:

1. Real process environment variables always win.
2. Database-backed admin configuration comes next.
3. `.env`, `.env.local`, and `.env.local.php` provide defaults and local bootstrap values.

Setup may write initial values such as site title and site URL into database-backed configuration after the database is available. `.env.local.php` remains suitable for early bootstrap values such as `APP_SECRET` and environment-specific setup before the database-backed configuration layer can be read.

Protected configuration values such as provider API keys should be readable and writable only by administrators. They may be stored as plain database values initially because normal users cannot access the database directly, but the storage boundary should allow later encryption-at-rest if a concrete requirement appears. If encryption is added, reversible encryption must use an application secret/key because these values must be read back by the application.

Configuration changes should be logged through the normal logging/audit path with safe metadata such as actor, key/group, old/new value redaction where needed, and timestamp. A separate admin audit log remains an implementation option and should be decided when logging retention and log categories are defined.

### Implementation order

1. Define the smallest core namespace and result/extension conventions needed by the first real feature.
2. Implement recoverable error and validation patterns before complex administrative workflows.
3. Define static/dynamic content boundaries before schema fields, editor flows, import/export, or search.
4. Define theme resolution before plugin modules are allowed to contribute templates or assets.
5. Define module discovery and lifecycle before modules can contribute routes, services, permissions, migrations, or assets.
6. Define event and Messenger conventions before broad side-effect workflows such as indexing, logging, statistics, or mail dispatch.
7. Add operational features such as backup, restore, self-update, and release packaging only after the core content and module boundaries are stable enough to protect user data.

## Testing & Validation
- Run `php -l <path>` for changed PHP files.
- Run targeted PHPUnit tests for changed service, controller, entity, form, validator, or command behavior.
- Run `php bin/console lint:container` after service wiring, configuration, event subscriber, message handler, security, or module lifecycle changes.
- Add integration tests for every documented extension point before relying on it from another feature.
- Add resolver tests for replaceable strategies, including default selection, priority handling, configuration selection, and invalid contribution handling.
- Test configuration precedence for real environment variables, database-backed admin configuration, and `.env` defaults once the configuration service exists.
- Test administrator-only access to global configuration and protected configuration values.
- Add event or Messenger tests when behavior depends on dispatching, consuming, or ordering side effects.
- Run `.codex/compare_translations.php` when user-facing copy is added or changed.
- Use `.codex/render.php /<route>` for rendered Twig review when routes, templates, translations, or editor UI change.
- Keep `dev/CLASSMAP.md` updated for public behavior entry points such as controllers, commands, services with contributor-facing behavior, event subscribers, voters, Twig extensions, and module lifecycle hooks.

## Implementation Notes
- **Decision recorded:** Use the proposed namespace grouping as the starting point. Larger namespaces are acceptable when their internals stay modular, small, and easy to review.
- **Decision recorded:** Use a lightweight `.manifest`-style metadata format based on `KEY=VALUE` pairs for application, plugin module, and theme metadata unless a later draft identifies a concrete limitation.
- **Decision recorded:** Manifest parsing is domain-neutral. Required keys are not hardcoded in the parser and must be supplied by feature-specific manifest specifications or validators. Namespaced specs should receive namespace and short key names separately to avoid duplicate allowlists and keep future app, theme, and module manifests consistent.
- **Decision recorded:** Replacement behavior is not automatically event-based. Each replacement point must define its own selection mechanism. Events may participate when negotiation is needed, but simple provider replacement should prefer explicit resolvers, service decoration, or configuration.
- **Decision recorded:** An event is public only when it is documented as a module or theme extension point or listed as a stable extension contract. Undocumented events are internal lifecycle events and may change with their owning feature. Before `1.0.0`, public events may still change when drafts, tests, documentation, and callers are updated together.
- **Decision recorded:** Module migrations are allowed before `1.0.0`, but must use a single consistent core-owned migration workflow based on Symfony and Doctrine conventions. Module-owned tables are preferred for module domain data; variable fieldsets remain focused on flexible content structures and content-like extension data.
- **Decision recorded:** The initial API scope is content interaction only. Internal process control and operational workflows are deferred unless a future API draft explicitly adds them.
- **Decision recorded:** Global admin configuration uses database-backed configuration once persistence exists and is readable/writable only by the `Administrators` ACL group.
- **Decision recorded:** Configuration precedence is real environment variables, then database-backed admin configuration, then `.env`/`.env.local`/`.env.local.php` defaults.
- **Decision recorded:** User-specific API tokens belong to user profile settings, while project-specific overrides belong to project/content fields rather than global configuration keys.
- **Decision recorded:** Protected configuration values may start as ACL-protected database values, with reversible encryption kept possible but not required unless a concrete need appears.
- Prefer documenting constraints before building abstractions. If a future feature only needs to remain possible, capture the constraint in the relevant draft instead of adding speculative code.
- Future-facing features such as CommunityHub, inline frontpage editing, and REI3 tickets integration should influence boundaries, but should not expand the first core implementation unless they expose a blocking architecture issue.
