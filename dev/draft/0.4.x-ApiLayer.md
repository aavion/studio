# API layer (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-06-06  
> **Owner**: Core  
> **Purpose:** Draft for external API capabilities, REST conventions, authentication, and module extensibility.  

## Overview
- Defines whether and how the CMS exposes API endpoints.
- Covers REST conventions, authentication, serialization, permissions, versioning, and module-provided endpoints.
- Depends on the content model, security, and import/export drafts.
- Limits the first API scope to content interaction.

## Outline
The first API should expose content interaction, not internal process control. External clients should be able to read content and, where explicitly allowed, create or update content through content-oriented operations. Content API responses should preserve durable UIDs, language, generic variant, version, and schema field identifiers where applicable. API access requires scoped API tokens generated, revoked, and reset by users. Administrative internals such as package lifecycle, update flows, backup/restore, release packaging, and general command execution should stay outside the initial API.

The API should be boring and predictable. REST-style endpoints, Symfony controllers, Serializer, Validator, voters, and clear error formats are enough for the first phase. More advanced API styles can be revisited only when a real need appears.

API tokens are user-owned settings. Users should manage their own scoped API tokens from their profile/account configuration, not from global admin configuration. Administrators may need oversight or revocation tools later, but token creation/reset remains tied to the owning user context so audit and ACL behavior stay clear.

Module-provided API resources should be possible later, but only after module permissions, routing, and serialization contracts are stable.

## Planning Readiness
This draft is sufficient as a product baseline for the API feature branch, but the implementation plan should start by locking the concrete first slice before code changes. Use the API branch to decide and document:

- The first shipped endpoint set, preferably read-only published content list/detail endpoints before write endpoints unless the feature branch explicitly needs writes.
- The exact API token scope names and permission mapping, for example content read, content write, and future package-owned scopes.
- The stable JSON response envelope, error envelope, validation-error shape, pagination metadata, resource links, and versioned route names under `/api/v1`.
- The first content response DTO/read-model shape, including which content status, visibility, language, variant, version, slug, URL, schema, and field values are safe to expose.
- The documented filtering and sorting fields for list endpoints, with portable database/read-model behavior instead of JSON-field filtering that only works on one database engine.
- The write boundary, if implemented in the first branch: dedicated command DTOs, Symfony Validator constraints, ACL/voter checks, optimistic conflict handling, audit logging, and status transition rules.
- The authentication boundary: no browser-session assumptions, token lookup through the existing prefix/HMAC/encrypted payload model, revoked-token denial, user-context attribution, rate-limit hooks, and redacted diagnostics.
- Deferred module-provided API resources, `ApiResponseContextEvent`, and broader API extension points until the core response model and package permission contracts are stable.

## Technical Specifications
- Use Symfony controllers for API endpoints.
- Use Symfony Serializer for normalized content output.
- Use Symfony Validator for input payload validation.
- Use voters or dedicated permission checks for API access.
- Require scoped API tokens for all API access.
- Store API keys with a short non-secret prefix, an HMAC lookup hash, and a reversibly encrypted key payload so users can reveal keys again after re-authentication.
- Derive API-key HMAC and encryption material from `APP_SECRET` for the first implementation.
- Support API key status values for read-only, read-write, and revoked keys, with enum-owned label keys and permission semantics.
- Let users generate, revoke, and reset scoped API tokens.
- Keep scoped API token management in user profile/account settings.
- Associate API token usage with the owning user so edits can be audited and ACL checks can use user context.
- Prefix API routes predictably and version them from the start, for example `/api/v1`.
- Reserve `/api/live/**` for application-owned live JSON flows such as captcha seeds, polling, and operation status checks. This branch is intentionally not part of the stable external versioned API contract.
- Use `/api/live/operations/{operationId}?token=<token>&cursor=<number>` for ActionLog polling fallback responses. Payloads should include `operation_id`, `status`, `cursor`, optional `cursor_max`, `entries`, and `next_poll_ms`.
- Treat live-operation cursors as monotonic numeric positions emitted by the log producer, not as stable durable identifiers.
- Defer public content DTO and serializer contracts to the API feature branch so entity exposure, pagination, error payloads, and versioning rules are decided together.
- Version the API only when breaking changes need to be managed; do not add version complexity prematurely.
- Return deterministic JSON error payloads for validation, authorization, not found, conflict, and server errors.
- Support pagination for list endpoints.
- Support filtering and sorting only for documented fields.
- Keep content identifiers stable and separate from public URLs.
- Expose durable content UIDs instead of relying on slugs as identifiers.
- Include language, generic variant, version, publication status, and visibility context in content representations when relevant and safe.
- Include field identifiers in schema-driven field output so clients can map values back to schema definitions.
- Include safe required schema fields such as `title` and `subtitle` in content representations when the endpoint scope supports generic previews, menus, or list views.
- Do not expose internal audit metadata, ACL group details, or author/editor identities unless the endpoint explicitly requires them and permissions allow it.
- Enforce content ACL restrictions before returning API content.
- Expose schema metadata only when it is safe and useful for clients.
- Allow read-only endpoints before write endpoints if that reduces risk.
- Keep API authentication separate from browser session assumptions.
- Add `ApiResponseContextEvent` only after the API response model exists. It is a useful candidate for safe diagnostics or debug metadata, but should not be implemented before response shape, permissions, and redaction rules are concrete.
- Use the shared JSON response/error rendering boundary for both `/api/v1/**` and internal `/api/live/**` endpoints so cache headers, no-store behavior, translation keys, and Message-layer diagnostics stay consistent.
- Keep API DTOs, request DTOs, response builders, authenticators, voters, and read models out of Symfony service discovery when they are plain values; register only real services.

## Testing & Validation
- Functional-test every endpoint with allowed and denied access.
- Test API access is denied without a valid scoped token.
- Test token revocation and reset behavior.
- Test API key HMAC hashes and encrypted payloads are stored instead of raw tokens.
- Test users can reveal an existing API key only after re-authentication.
- Test users manage their own scoped API tokens from profile/account settings.
- Test API writes are attributed to the token owner.
- Test validation errors and error payload shape.
- Test pagination, filtering, and sorting once supported.
- Test serialization does not expose internal fields or secrets.
- Test ACL-restricted content is omitted or denied for unauthorized API clients.
- Test content status visibility, for example draft versus published.
- Test language and generic variant API output separately.
- Test field identifiers are present when schema-driven fields are serialized.
- Test safe preview-field serialization separately from internal audit, ACL, and entity metadata.
- Test module-provided API resources only after module API contracts exist.
- Test internal `/api/live/**` payloads use the shared JSON output renderer and no-store response headers.
- Test ActionLog polling honors the supplied numeric cursor and exposes progress hints where available.
- Test API responses do not depend on current Twig templates, CSS classes, or frontend markup.
- Test list endpoints against documented pagination/filtering/sorting semantics and avoid assertions that depend on database row order without an explicit sort.

## Implementation Notes
- **Decision recorded:** Initial API scope is content interaction only.
- **Decision recorded:** Content API representations should use durable UIDs and include language, variant, version, status, visibility context, and field identifiers where relevant, while protecting internal audit and ACL details by default.
- **Decision recorded:** Safe required schema fields such as `title` and `subtitle` may be exposed for generic previews, menus, and list views when endpoint scope allows it.
- **Decision recorded:** Start REST-style with Symfony controllers and Serializer, using established REST conventions for request/response shape, status codes, validation errors, pagination, filtering, and resource URLs.
- **Decision recorded:** Start with read-only content endpoints if write behavior is not needed immediately.
- **Decision recorded:** API authentication uses scoped API tokens. Users can generate, revoke, and reset tokens; token usage is associated with the owning user for ACL and audit behavior.
- **Decision recorded:** Scoped API tokens are user-owned profile/account settings, not global admin configuration.
- **Decision recorded:** API keys are stored as `prefix`, `hmac_hash`, and `encrypted_key`. The prefix supports display/diagnostics, the HMAC supports lookup, and the encrypted payload supports password-gated reveal flows. Use `APP_SECRET` as the first encryption/HMAC root secret.
- **Decision recorded:** API key encryption/HMAC behavior should move to the shared `APP_SECRET`-rooted, context-labeled, versioned secret protector once that foundation exists.
- **Decision recorded:** API key lifecycle states are `read_write`, `read_only`, and `revoked`. Status labels and simple permission semantics live on the API key status enum so later UI, CLI, and API handlers can reuse the same rules.
- **Decision recorded:** Revoked API keys remain audit-relevant after their original user account is purged. Deleted-user cleanup reassigns retained revoked keys to a stable system deleted-user account, and future API-audit review of revoked-key usage should trigger a warning mail to the original affected user when an address is still known.
- **Decision recorded:** API writes should use dedicated command DTOs plus Symfony Validator rather than browser form objects.
- **Decision: provisional until API:** Final API response DTO/read-model shape is intentionally deferred to the API feature branch. Public API responses should not expose Doctrine entities or template-specific arrays unless the API branch explicitly decides and documents a stable serializer contract.
- **Decision recorded:** Use `/api/v1` as the first API version prefix.
- **Decision recorded:** Use `/api/live/**` for internal live JSON endpoints that are fetched by system or public UI JavaScript and should not consume top-level content routes.
- **Decision recorded:** `/api/live/**` remains outside the stable external API contract. External integrations should use versioned routes such as `/api/v1/**`; live routes are application-owned internal JSON flows.
- **Decision recorded:** ActionLog polling under `/api/live/operations/**` uses a numeric `cursor` query parameter plus optional `cursor_max` progress metadata and a per-run token instead of route authentication.
- **Decision recorded:** Defer `ApiResponseContextEvent` until real API response builders exist; it should extend safe diagnostics or debug context, not bypass serialization, permission, or redaction rules.
- **Decision recorded:** The API feature branch should start with a concrete endpoint/resource plan before implementation. The plan must name the first endpoints, token scopes, DTO/read-model shapes, error envelope, pagination/filtering/sorting behavior, security checks, audit events, and deferred extension points.
- **Decision recorded:** Module-provided API resources remain deferred until the core `/api/v1` response model, token-scope contract, package permission policy, and serializer/redaction rules are stable enough to validate package-owned routes.
- **Open for API branch:** Decide whether the first feature-complete API PR includes write endpoints or deliberately ships read-only content endpoints plus token management and stable error/pagination contracts.
