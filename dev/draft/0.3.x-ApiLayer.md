# API layer (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for external API capabilities, REST conventions, authentication, and module extensibility.

## Overview
- Defines whether and how the CMS exposes API endpoints.
- Covers REST conventions, authentication, serialization, permissions, versioning, and module-provided endpoints.
- Depends on the content model, security, and import/export drafts.
- Limits the first API scope to content interaction.

## Outline
The first API should expose content interaction, not internal process control. External clients should be able to read content and, where explicitly allowed, create or update content through content-oriented operations. Content API responses should preserve durable UIDs, language, generic variant, version, and schema field identifiers where applicable. Administrative internals such as module lifecycle, update flows, backup/restore, release packaging, and general command execution should stay outside the initial API.

The API should be boring and predictable. REST-style endpoints, Symfony controllers, Serializer, Validator, voters, and clear error formats are enough for the first phase. More advanced API styles can be revisited only when a real need appears.

Module-provided API resources should be possible later, but only after module permissions, routing, and serialization contracts are stable.

## Technical Specifications
- Use Symfony controllers for API endpoints.
- Use Symfony Serializer for normalized content output.
- Use Symfony Validator for input payload validation.
- Use voters or dedicated permission checks for API access.
- Prefix API routes predictably, for example `/api`.
- Version the API only when breaking changes need to be managed; do not add version complexity prematurely.
- Return deterministic JSON error payloads for validation, authorization, not found, conflict, and server errors.
- Support pagination for list endpoints.
- Support filtering and sorting only for documented fields.
- Keep content identifiers stable and separate from public URLs.
- Expose durable content UIDs instead of relying on slugs as identifiers.
- Include language, generic variant, version, publication status, and visibility context in content representations when relevant and safe.
- Include field identifiers in schema-driven field output so clients can map values back to schema definitions.
- Include safe metadata such as `title` and `subtitle` in content representations when the endpoint scope supports generic previews, menus, or list views.
- Do not expose internal audit metadata, ACL group details, or author/editor identities unless the endpoint explicitly requires them and permissions allow it.
- Enforce content ACL restrictions before returning API content.
- Expose schema metadata only when it is safe and useful for clients.
- Allow read-only endpoints before write endpoints if that reduces risk.
- Keep API authentication separate from browser session assumptions.

## Testing & Validation
- Functional-test every endpoint with allowed and denied access.
- Test validation errors and error payload shape.
- Test pagination, filtering, and sorting once supported.
- Test serialization does not expose internal fields or secrets.
- Test ACL-restricted content is omitted or denied for unauthorized API clients.
- Test content status visibility, for example draft versus published.
- Test language and generic variant API output separately.
- Test field identifiers are present when schema-driven fields are serialized.
- Test safe metadata serialization separately from internal audit and ACL metadata.
- Test module-provided API resources only after module API contracts exist.

## Implementation Notes
- **Decision recorded:** Initial API scope is content interaction only.
- **Decision recorded:** Content API representations should use durable UIDs and include language, variant, version, status, visibility context, and field identifiers where relevant, while protecting internal audit and ACL details by default.
- **Decision recorded:** Safe flexible metadata such as `title` and `subtitle` may be exposed for generic previews, menus, and list views when endpoint scope allows it.
- **Decision proposed:** Start REST-style with Symfony controllers and Serializer.
- **Decision proposed:** Start with read-only content endpoints if write behavior is not needed immediately.
- **Decision required:** Decide first API authentication mechanism.
- **Decision required:** Decide whether API writes use direct content forms/validators or dedicated command DTOs.
- **Decision required:** Decide API versioning approach before first public release.
