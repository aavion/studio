# Draft and publish workflow (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for editorial drafts, autosave, review, commit/publish actions, version activation, and concurrency handling.  

## Overview
- Defines how editors safely move content from draft work to published versions.
- Covers autosave, explicit save, preview, review, commit messages, publish/archive actions, version history, locks, and conflict handling.
- Depends on content model, error handling, security/ACL, system UI, schema fields, and editor experience.
- Provides the workflow layer that makes structured content authoring safe for real editorial work.

## Outline
The content model defines versions and statuses, but a CMS also needs an editorial workflow around those states. Editors should be able to work on drafts, preserve partial input, preview changes, compare against the active version, commit a new version, and publish or archive content through explicit actions.

The first workflow should avoid hidden autosave behavior becoming destructive. Autosave and draft snapshots may preserve work, but activation should remain explicit. Publishing should be auditable, permission-checked, and recoverable through version history.

Concurrency should be handled early. The system should prevent silent overwrites when two users edit the same content. The first implementation may use optimistic locking and clear conflict messages before more advanced collaborative editing exists.

API-assisted and LLM-assisted workflows should not become a parallel publishing model. They may use Sanity-like revision, validation, and mutation ergonomics as a broad reference, but they must flow through the same draft, diff, conflict, permission, audit, and publish boundaries as the web editor.

## Technical Specifications
- Support draft states separate from active/published content versions.
- Provide autosave or draft snapshots through the editor with configurable retention.
- Provide explicit actions for save draft, preview, commit version, publish, schedule, archive, restore previous version, and discard draft where supported.
- Keep publish and archive actions permission-protected through voters.
- Store audit metadata for draft owner, last editor, commit actor, publish actor, timestamps, and optional commit message.
- Use Symfony Lock or optimistic version checks to prevent stale overwrite.
- Show conflict recovery UI when a draft is based on an outdated version.
- Provide diff/review support before committing generated, imported, or destructive changes.
- Dispatch documented events after commit, publish, archive, restore, and discard where later indexing/export/cache workflows need them.
- Keep publish workflows compatible with language variants and generic variants.
- Keep field validation and schema Twig validation blocking before commit or publish.
- Let modules observe workflow events only through documented extension points.
- Route editor actions, API mutations, imports, and LLM-generated proposals through shared workflow services so validation, optimistic locking, diffs, audit, and publish outcomes stay consistent.

## Testing & Validation
- Test draft creation, autosave, explicit save, commit, publish, archive, restore, and discard flows.
- Test stale draft/conflict behavior.
- Test permission checks for commit and publish actions.
- Test validation blocks invalid field values and invalid schema Twig before activation.
- Test version history preserves durable content UID.
- Test workflow events only fire after successful state changes.
- Test generated/imported changes require review where configured.

## Implementation Notes
- **Decision recorded:** Draft/autosave state must not silently replace the active version; activation remains explicit.
- **Decision recorded:** Publish and archive are permission-checked, audited workflow actions.
- **Decision recorded:** Concurrency protection belongs in the first workflow implementation to avoid silent data loss.
- **Decision recorded:** API and LLM collaboration may adopt Sanity-like ergonomics, but the web editor remains the preferred workflow and all channels must share the same domain workflow boundaries.
- **Open:** Decide the first storage shape for drafts and autosave snapshots during editor implementation.
- **Open:** Decide whether the first release uses a separate commit step or combines commit and publish for simple content types.
