# Frontend delivery and caching (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for public content delivery, snapshot/cache boundaries, HTTP caching, invalidation, and performance-oriented rendering.  

## Overview
- Defines how public content is rendered and delivered after editorial changes.
- Covers read models, cache layers, invalidation, frontend routing, HTTP headers, performance diagnostics, and maintenance actions.
- Depends on content model, theme engine, draft/publish workflow, resolver/search, media library, and operational security.
- Keeps public delivery fast and predictable without tying the authoring model directly to every request.

## Outline
Public website delivery should be deterministic and efficient. The authoring model may be flexible and relational, but public rendering should use a stable read path with clear invalidation rules. This avoids every page request becoming a deep traversal of schemas, references, media, permissions, and resolver outputs.

The first implementation does not need a complex static-site generator, but it should define delivery boundaries early. Published content can be rendered through controlled services, cached read models, snapshot-like metadata, or later generated artifacts. The important rule is that publish events invalidate or rebuild the exact data public routes depend on.

Caching should stay Symfony-native first: HTTP cache headers, `cache.app`, filesystem cache by default, AssetMapper hashed assets, and optional adapters later. Admin tools should show enough cache and delivery status that operators can recover from stale output without shell access.

## Technical Specifications
- Define public delivery services separate from editor/admin write services.
- Use content route resolver output, theme resolver output, schema rendering, media URLs, and resolver context through a controlled read path.
- Provide cache namespaces for public content rendering, navigation/menu data, resolver outputs, schema rendering metadata, media metadata, and API read output where useful.
- Use HTTP caching headers such as `ETag`, `Last-Modified`, and `Cache-Control` where safe.
- Use AssetMapper hashed asset URLs for long-lived frontend assets.
- Invalidate or rebuild affected cache entries after publish, archive, restore, schema activation, active package change, media change, import apply, or package lifecycle changes.
- Provide CLI commands for delivery/cache rebuild, warmup, prune, and diagnostics.
- Provide admin maintenance UI for cache clear/warmup and delivery status once operational UI exists.
- Keep snapshot-like export/read artifacts optional and adapter-backed until a concrete performance need requires them.
- Include public delivery behavior in backup/restore and self-update compatibility checks when generated artifacts or metadata are involved.
- Keep private or ACL-restricted content out of public cache entries unless the cache key and delivery path are permission-aware.

## Testing & Validation
- Test public route rendering uses published content only.
- Test cache invalidation after publish, archive, restore, schema change, media change, and theme change.
- Test `ETag`/`Last-Modified` behavior where implemented.
- Test ACL-restricted content is not leaked through public caches.
- Test rebuild/warmup/prune commands.
- Test admin maintenance actions for cache and delivery diagnostics once UI exists.
- Run asset build commands after frontend delivery asset changes.

## Implementation Notes
- **Decision recorded:** Public delivery should use a controlled read path separate from mutable editor workflows.
- **Decision recorded:** Symfony-native cache and HTTP headers are the first delivery foundation; external cache/CDN integrations remain optional.
- **Decision recorded:** Publish and lifecycle events must define cache invalidation or rebuild behavior.
- **Open:** Decide whether the first release needs persisted snapshot artifacts or only cache-backed read models.
- **Open:** Define default cache TTLs and invalidation namespaces after the first public rendering slice exists.
