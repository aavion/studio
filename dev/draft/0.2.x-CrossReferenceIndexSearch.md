# Cross-reference index and search (Feature Draft)

> **Status**: Draft  
> **Updated**: 2026-05-20   
> **Owner**: Core  
> **Purpose:** Draft for automatic cross-reference resolution, content indexing, and search behavior.

## Overview
- Defines how content references are detected, stored, resolved, and displayed.
- Covers search indexing, relationship discovery, and future neural-like content indexing.
- Depends on the content model, schema-driven fields, and import/export format decisions.
- Creates a foundation for broken-link detection, related content, search, and later semantic indexing.

## Outline
The CMS should understand relationships between content items instead of treating every page as isolated text. References may come from explicit content reference fields, links in rich text, media references, taxonomy-like fields, imports, module data, or future generated suggestions.

The first cross-reference system should focus on deterministic references: content UIDs, slugs, URLs, media IDs, field identifiers, language variants, generic variants, and field-level references. Later semantic or neural-like indexing can be added as an enhancement without replacing the deterministic index.

Search should begin with database-backed indexing if practical, then allow replacement with a dedicated adapter later. The architecture should make search adapters replaceable without coupling content storage to one search engine.

## Technical Specifications
- Define reference records with source, target, reference type, field/path, and status.
- Include language and generic variant context in reference records when the reference is variant-specific.
- Include field identifiers when references originate from schema-driven field values.
- Track broken, unpublished, moved, and external references distinctly.
- Respect content visibility and ACL restrictions when returning search results or related-content suggestions.
- Update references after content save, publish, import, delete, restore, and schema migration operations.
- Use Messenger for rebuilds or expensive indexing work.
- Use events for lifecycle notification such as content indexed or broken reference detected when documented.
- Define a `SearchAdapter`-style replacement point before adopting external search.
- Keep deterministic reference resolution separate from future semantic indexing.
- Support rebuild commands for references and search indexes.
- Make import/export preserve stable content identifiers and reference intent where possible.
- Provide admin diagnostics for broken references and stale indexes.

## Testing & Validation
- Test explicit content reference fields.
- Test references for language-specific and generic-variant-specific field values.
- Test field identifier tracking in reference records.
- Test references extracted from rich text or markdown once those editors exist.
- Test broken, moved, unpublished, and deleted targets.
- Test ACL-restricted content is not returned in search or related-content results for unauthorized users.
- Test index rebuilds are idempotent.
- Test search adapter replacement and default adapter behavior.
- Test import/export round trips preserve references.
- Test Messenger indexing handlers where asynchronous rebuild is used.

## Implementation Notes
- **Decision proposed:** Start with deterministic reference indexing before semantic indexing.
- **Decision recorded:** Deterministic reference records should preserve content UID, field identifier, language, and generic variant context when available.
- **Decision recorded:** Search and related-content output must respect content visibility and ACL restrictions.
- **Decision proposed:** Keep search adapter replaceable from the start, but use a simple default adapter first.
- **Decision proposed:** Use Messenger for expensive rebuilds.
- **Decision required:** Decide whether the first search implementation uses database `LIKE`, full-text features, or a small custom index table.
- **Decision required:** Decide how external URLs are checked and how often.
